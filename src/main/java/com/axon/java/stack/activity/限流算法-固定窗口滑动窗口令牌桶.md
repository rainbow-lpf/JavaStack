# 限流算法：固定窗口、滑动窗口、令牌桶

> 三种最常用的限流算法，从直觉到实现，彻底区分。

---

## 一、固定窗口（Fixed Window）

### 直觉

时间轴切成一段段固定的格子（如每 60 秒一格），只统计**当前格子**内的请求数。

```
  [第1分钟]  [第2分钟]  [第3分钟]  ...
     |          |          |
   计 0~100   计 0~100   计 0~100
   到点清零    到点清零    到点清零
```

### 实现

```
Redis: INCR key  +  EXPIRE key 60
      计数 > limit 则拒绝，key 到 60 秒自动清零
```

### 致命缺陷：临界突发

```
限流 100 次/分钟：
  第 1 分钟最后 1 秒（59.9s）打满 100 次
  第 2 分钟开始（60.0s）计数清零，又能打 100 次
  → 实际 1 秒内涌进 200 次 ❌
```

## 二、滑动窗口（Sliding Window）

### 直觉

窗口是"从现在往前推 N 秒"的**连续滚动区间**，没有固定边界。

```
任意时刻统计：最近 60 秒内请求数
时间每过一秒，窗口就往前滑一秒，掉出区间的请求自动失效
```

### 为什么没有临界突发

```
限流 100 次/分钟：
  上 59.9 秒打了 100 次
  → 现在统计的"最近 60 秒"里已经有 100 次
  → 接下来 1 秒内必然被限制 ✅
```

### 实现（Redis ZSet）

```java
public boolean isAllowed(String key, int windowSizeInSeconds, int limit) {
    long now = System.currentTimeMillis();
    long windowStart = now - windowSizeInSeconds * 1000L;

    // ① 移除窗口外的旧数据
    zset.removeRangeByScore(0, true, windowStart, false);

    // ② 统计窗口内请求数
    long count = zset.count(windowStart, true, now, true);

    // ③ 未超限则放行并记录
    if (count < limit) {
        zset.add(now, identifier + ":" + now);
        return true;
    }
    return false;
}
```

## 三、令牌桶（Token Bucket）

### 直觉：水桶装令牌

```
一个桶，容量 10 个令牌
有人每秒往桶里放 1 个令牌
桶满了 → 多余的令牌直接溢出丢弃
请求来了 → 必须拿走 1 个令牌才放行
拿不到令牌 → 拒绝
```

### 三个参数决定一切

| 参数 | 含义 | 控制什么 |
|------|------|------|
| `rate` | 每秒放几个令牌 | 长期平均速率 |
| `capacity` | 桶最多装几个 | 允许的突发量 |
| `tokens` | 当前剩几个 | 动态状态 |

```
例 rate=2, capacity=10：
  桶满 10
  瞬间来 10 个请求 → 一次拿光，全放行 ✅（突发）
  桶空 → 每秒补 2 → 每秒最多放 2（回归匀速）
```

### 关键认知：补充永不停止

```
补充线：每秒固定补 rate 个，永不停止
消耗线：请求来了拿一个
桶满：装不下 → 直接溢出丢弃（不是暂停等消耗）

❌ 错误理解：满了要等消耗释放才能再塞
✅ 正确理解：一直在塞，满了就溢出去
```

### 实现：惰性计算，不开定时线程

```java
class TokenBucket {
    double capacity;   // 桶容量
    double rate;       // 每秒补充令牌数
    double tokens;     // 当前令牌数
    long lastTime;     // 上次补充时间

    boolean tryAcquire() {
        long now = System.nanoTime();

        // ① 按经过时间补令牌，补到容量上限
        tokens = Math.min(capacity, tokens + (now - lastTime) / 1e9 * rate);
        lastTime = now;

        // ② 有令牌则扣一个放行
        if (tokens >= 1) {
            tokens -= 1;
            return true;
        }
        return false;
    }
}
```

```
请求 1：桶 10，拿 1 → 剩 9
请求 2（1 秒后）：先补 2 → 11，超容量 → 桶 10，拿 1 → 剩 9
请求爆发：1 秒来 20 个 → 拿 9 个后桶空，剩 11 个拒绝
```

### 为什么允许突发

```
令牌桶管"速率 + 容量"，不管"格内总数"
平时流量低 → 令牌攒着
高峰来了 → 攒的令牌一次性冲一波
长期平均 = rate ✅
```

## 四、三算法对比

| | 固定窗口 | 滑动窗口 | 令牌桶 |
|------|------|------|------|
| 本质 | 按格子计数 | 按滚动区间计数 | 令牌速率 |
| 边界 | 固定，到点清零 | 连续滚动 | 无边界概念 |
| 临界突发 | ❌ 会翻倍 | ✅ 无 | ✅ 受容量限制 |
| 允许突发 | 不允许 | 不允许 | ✅ 允许（容量内） |
| 实现 | INCR+EXPIRE，极简 | ZSet/环形数组/队列 | 计数器+时间戳 |
| 内存 | 1 个计数 | 存窗口内请求 | 2 个变量 |
| 精度 | 粗 | 细 | 中（平滑） |

### 适用场景

```
固定窗口 ：粗粒度、要求不高（简单接口限流）
滑动窗口 ：精确控"一段时间总数"（接口级精确限流）
令牌桶   ：允许瞬时突发（网关、秒杀）
漏桶     ：强制匀速输出（平滑流量，不允许多余突发）
```

## 五、易混点澄清

```
① 滑动窗口底层不是令牌桶 —— 两者平级，是不同算法
   滑动窗口 = 计数式（看总数）
   令牌桶   = 速率式（看速率+容量）

② Guava RateLimiter 底层 = 令牌桶（SmoothBursty）
③ Redis 滑动窗口 = ZSet（滑动窗口日志）
④ Redis 固定窗口 = INCR + EXPIRE
```

---

## 六、一句话总结

```
固定窗口：固定格子，格内计数，到点清零 → 有临界突发
滑动窗口：连续滚动，统计最近 N 秒总数 → 无临界突发
令牌桶：  定速补、满了溢、请求扣 → 控均值 + 允突发
```

> **令牌桶核心纠偏：补充永不停止，桶满只是溢出丢弃，不是"等消耗释放才能再塞"。**
