## 1. Redis 有哪些数据类型？各自适用什么场景？

**回答话术：**

> 「Redis 五大基本类型：String、Hash、List、Set、ZSet。扩展还有 Bitmap、HyperLogLog、Geo、Stream。
>
> **String**：最基础，存 JSON、分布式锁、计数器、Session。
> **Hash**：存对象，用户信息、配置项。比 String JSON 省内存，可单独读写字段。
> **List**：消息队列、时间线。LPUSH + BRPOP 做阻塞队列。
> **Set**：标签、共同好友、去重。交并差集操作。
> **ZSet**：排行榜、延时队列。score 分权，zrangebyscore 按区间取。
> **Bitmap**：签到、在线状态。1 位 1 个用户。
> **HyperLogLog**：UV 统计。12KB 内存统计 2^64 个不重复元素，误差 0.81%。
> **Geo**：附近的人、距离计算。
> **Stream**：持久化消息队列，消费组、ACK 机制。」

## 2. Redis 为什么这么快？

**回答话术：**

> 「四点：① **纯内存操作**，没有磁盘 I/O 开销；② **单线程 + IO 多路复用**，避免了上下文切换和锁竞争；③ **高效数据结构**，底层用跳表、压缩列表、SDS 等精心设计；④ **事件驱动 + Reactor 模型**，一个线程处理海连接。总结：内存快、无锁快、结构快。」

---

## 3. Redis 如何删除过期 Key？

**回答话术：**

> 「三种策略组合：**惰性删除 + 定期删除**，定时删除不用。
>
> **惰性删除**：客户端访问 key 时检查是否过期，过期则删。优点不额外消耗 CPU，缺点冷数据一直占内存。
> **定期删除**：每 100ms 随机抽取一批过期 key 检查删除，单次限时 25ms。在内存和 CPU 间平衡。
> **定时删除**：每个 key 一个定时器，精确但开销大，Redis 默认不用。
>
> 补充：如果到期没删，内存淘汰策略会兜底。生产常用 `allkeys-lru`。」

---

## 4. Redis 内存淘汰策略有哪些？

**回答话术：**

> 「8 种，分两类：**不淘汰**和**淘汰**。
>
> | 大类 | 策略 | 说明 |
> |------|------|------|
> | 不淘汰 | `noeviction` | 内存满了直接报错 |
> | 从有 TTL 的 key 中淘汰 | `volatile-lru/lfu/random/ttl` | |
> | 从所有 key 中淘汰 | `allkeys-lru/lfu/random` | **生产最常用** |
>
> **LRU vs LFU**：LRU 看"最近是否被访问"，适合热点缓存。LFU 看"访问频率"，适合防止偶发大流量把热数据挤掉。
> 我司一般用 `allkeys-lru`，如果存在明显冷热不均用 `allkeys-lfu`。」

## 5. 缓存穿透 / 击穿 / 雪崩 是什么？怎么解决？

| 问题 | 什么现象 | 怎么解决 |
|------|------|------|
| **缓存穿透** | 查不存在的数据，绕过缓存直接打 DB | 布隆过滤器过滤非法 key；空结果也缓存（TTL 短） |
| **缓存击穿** | 某个热点 key 过期，瞬间大量请求打 DB | 互斥锁只让一个线程回源；永不过期 + 异步刷新 |
| **缓存雪崩** | 大量 key 同时过期 / Redis 宕机，DB 瞬间压垮 | TTL 加随机值（如 300±60s）；主从 + 哨兵 / 集群 高可用；多级缓存；限流熔断 |

**回答话术（一口气版）：**

> 「**穿透**：查不存在的数据。布隆过滤器挡回去，或空结果缓存短 TTL。
> **击穿**：热点 key 过期。互斥锁只让一个线程查 DB 重建缓存。
> **雪崩**：大量同时过期或 Redis 宕机。TTL 加随机值分散过期时间，集群高可用，多级缓存兜底。」

## 6. 大 Key 会引发哪些问题？怎么发现和处理？

**回答话术：**

> 「大 Key 危害五个：**① 主线程阻塞**，DEL 大集合卡顿导致所有请求超时；**② 集群内存不均**；**③ 网络带宽打满**；**④ 主从同步延迟**；**⑤ 慢查询**。
>
> 发现：`redis-cli --bigkeys` 扫描、RDB 离线分析、`MEMORY USAGE`、慢查询日志。
>
> 处理：
> - **防**：String 压缩/只存索引、Hash 按维度或分桶拆、List 按时间分片、Set/ZSet 分桶 + Top-N 截断。
> - **删**：`UNLINK` 异步删，或分批 `SCAN + 小次 SREM` 循环。
> - **配置**：开 lazyfree 系列参数，过期/淘汰走异步。」

## 7. 哨兵模式原理是什么？

**回答话术：**

> 「哨兵 = Redis 高可用方案。三个角色：主节点 Master、从节点 Slave、哨兵 Sentinel。
>
> 四个核心功能：
> **① 监控**：哨兵定期 PING 主从节点。单个哨兵认为下线叫 SDOWN，多数哨兵投票确认叫 ODOWN。
> **② 自动故障转移**：主节点 ODOWN → 哨兵集群 Raft 选出一个 Leader → Leader 从 Slave 中选一个做新 Master（比较复制偏移量、运行 ID 等）→ 重新配置其他 Slave 指向新 Master。
> **③ 配置更新**：主从关系变化，哨兵自动推送。
> **④ 客户端通知**：客户端连哨兵获取当前 Master 地址，主挂了哨兵返回新 Master，客户端自动切换。」

---

## 8. 客户端连哨兵还是连主节点？

**回答话术：**

> 「连哨兵。客户端先连接哨兵，通过 `SENTINEL get-master-addr-by-name` 获取当前 Master 地址，再连 Master。主挂了哨兵选举新 Master，客户端订阅哨兵的 Pub/Sub 或定时问哨兵，拿到新地址自动切过去。直接连 Master 的话，主挂了客户端就死了。」

## 9. 缓存和数据库一致性怎么保证？

**回答话术：**

> 「强一致做不到，最终一致可以。核心思想：**先，再删缓存**。
>
> 为什么不是先删缓存再更新 DB？删了缓存 → 还没更新 DB → 有读请求把旧数据写入缓存 → 缓存又脏了。
>
> 先更 DB 再删缓存：更新 DB → 删缓存 → 下一个读请求查 DB 得到新值写缓存。小概率并发还脏 → 加**延迟双删**：更新 DB → 稍等几百 ms → 再删一次缓存。
>
> 终极方案：**Canal + binlog 异步同步**。监听 MySQL binlog 变化，异步更新/删除 Redis，解耦业务代码。」

---

## 10. Redis 分布式锁怎么实现？Redlock 是什么？

**回答话术：**

> 「单机 Redis：`SET key value NX PX 30000`，把加锁和设过期写成一个原子操作。解锁用 Lua 脚本 `if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1])`，防止误删别人的锁。
>
> 单机问题：主挂了锁丢失。**Redlock** 是 Redis 作者提出的多节点方案：向 N 个独立 Redis（建议 5 个）同时获取锁，超过半数（≥ N/2+1）成功才算获取成功。有争议，但思路是多节点投票防单点故障。
>
> 实际生产我倾向：单机 + 哨兵够用，或直接用 Redisson 封装好的 RedLock。」

---

## 11. Redisson 如何实现分布式锁？

**回答话术：**

> 「Redisson 基于 Redis 做了完善封装：① `tryLock` 用 `SET NX PX` 加锁；② 后台看门狗（Watchdog）每 10 秒续期，防止锁在任务完成前过期；③ 用 Redis 的 Pub/Sub 实现等待唤醒，而不是忙等自旋；④ 解锁用 Lua 保证原子性。
>
> 拿到锁 → 看门狗每 `lockTimeout/3` 续期一次 → 任务完成 → Lua 解锁。可重入用内部计数器实现。」

## 12. Redis 集群模式有哪些？各自优缺点？

| 模式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **主从** | 一主多从，读写分离 | 简单，读高并发 | 不能故障自动转移 |
| **哨兵** | 主从 + 哨兵监控，自动故障转移 | 高可用，自动切主 | 数据全量复制，单主写瓶颈 |
| **Cluster** | 16384 槽位分片，多主多从 | 横向扩展，数据分片，高并发写 | 跨槽操作受限，客户端需感知拓扑 |
| **Codis / Proxy** | 代理层转发 | 客户端无感知、运维简单 | 多一跳延迟，代理层自己也是瓶颈 |

**回答话术：**

> 「三种主流：① 主从，简单读多写少场景。② 哨兵，在主从上加监控和自动切换，高可用。③ Cluster，分片集群，数据按 16384 个槽分布多主，每主有从，水平扩展 + 自动故障转移。生产：数据量小用哨兵，海量数据用 Cluster。」

## 13. Redis 持久化方式：RDB vs AOF

| | RDB | AOF |
|------|------|------|
| **原理** | 定期快照整个内存到磁盘 | 每次写操作追加到日志 |
| **文件** | `dump.rdb` | `appendonly.aof` |
| **恢复速度** | 快 | 慢（需重放所有命令） |
| **数据安全** | 可能丢失最后两次快照间的数据 | 每秒 fsync，最多丢 1 秒 |
| **文件大小** | 小（压缩二进制） | 大（文本命令） |
| **重写** | — | BGREWRITEAOF 压缩 |

**回答话术：**

> 「RDB 是定时全量快照，恢复快但可能丢数据。AOF 是写命令日志，数据安全但文件大恢复慢。
> **生产建议**：两者都开。RDB 做冷备容灾，AOF 保数据完整。Redis 4.0 引入混合持久化，AOF 重写时把 RDB 二进制 + 增量 AOF 写一起，兼顾恢复速度和数据安全。」

## 14. Redis 事务和 MySQL 事务有什么区别？

**回答话术：**

> 「本质区别：**Redis 事务不支持回滚**。`MULTI` → 命令入队 → `EXEC` 依次执行，中间某条命令失败（语法错误全部不执行，运行时错误继续执行后面的），不会回滚已执行成功的命令。
>
> Redis 设计哲学：只有语法错误才是 bug，运行时错误不该导致整体回滚。
>
> **Lua 脚本**更常用做原子操作：`EVAL` 一段 Lua，在服务端原子执行，比 `MULTI/EXEC` 更灵活。」

---

## 15. Redis 管道（Pipeline）是什么？和事务有什么区别？

**回答话术：**

> 「管道：把多条命令一次发给 Redis，Redis 一次返回所有结果。减少 RTT（往返时间），但不保证原子性——中间可能插入其他客户端的命令。
>
> 事务：`MULTI/EXEC` 保证隔离性，中间不会插入其他命令，但不保证全部成功不失败。
>
> 管道 = 性能优化，事务 = 隔离性保证。两者可结合：`MULTI` → 管道批量发命令 → `EXEC`。」

---

## 16. Redis 为啥单线程还这么快？6.0 又为啥引入多线程？

**回答话术：**

> 「单线程快因为内存 + IO 多路复用 + 无锁。
>
> 6.0 引入多线程不是改命令执行，而是**网络 I/O 多线程**：多个线程处理 socket 读写和解析协议，命令执行仍然是单线程。原因是网络 I/O 成为瓶颈——10G 网卡下解析/写回数据耗时超过命令执行本身。I/O 多线程后 Redis 吞吐提升近 1 倍。」

---

## 17. Redis 中的热 Key 问题怎么处理？

**回答话术：**

> 「热 Key = 某个 key 的 QPS 远超其他。问题：单节点 CPU 瓶颈、网络瓶颈。
>
> 处理：
> - **二级缓存**：本地 Caffeine/Guava Cache 缓存热点 key，拦截大部分请求。
> - **分治**：把热 Key 复制多份，`hotkey:1`、`hotkey:2`... `hotkey:N`，客户端随机选一个读。
> - **读写分离**：读请求走从节点。
> - **迁移热点 key**：用 Redis Cluster 的 hotkey 迁移工具自动打散。」

## 18. Redis 底层数据结构有哪些？各自用在什么地方？

| 底层结构 | 用在哪些类型 | 特点 |
|------|------|------|
| **SDS（简单动态字符串）** | String | 二进制安全，O(1) 取长度，预分配防溢出 |
| **双向链表** | List（早期） | 内存开销大 |
| **压缩列表（ziplist）** | 小 Hash / 小 List / 小 ZSet | 连续内存，省内存，元素少时自动用 |
| **快速列表（quicklist）** | List（3.2+） | ziplist 组链表，Redis 3.2 起替代双向链表 |
| **跳表（skiplist）** | ZSet | O(log N) 范围查找，实现简单 |
| **哈希表（dict）** | Hash / Set | O(1) 查找 |
| **整数集合（intset）** | Set（全整数小集合） | 省内存，自动升级 |
| **listpack** | 小 Hash / 小 List（7.0+） | 替代 ziplist，解决连锁更新问题 |

**回答话术：**

> 「根据数据量和类型动态选底层。Hash 元素少用 ziplist（7.0 用 listpack），超过阈值转 dict。List 用 quicklist。ZSet 用 skiplist + dict。核心思想：小数据省内存用紧凑结构，大数据提速度用复杂结构。」
