> **总结日期：** 2026-07-07
> **核心主题：** Seata 四种分布式事务模式 XA、AT、TCC、Saga

---

## 一、四种模式概览

| 模式 | 核心思想 | 一致性 | 性能 | 侵入性 | 适用场景 |
|---|---|---|---|---|---|
| **XA** | 数据库 XA 协议，两阶段提交 | 强一致 | 差 | 无 | 对一致性要求极高的金融场景 |
| **AT** | 自动生成反向 SQL，一阶段提交 + 二阶段回滚 | 最终一致 | 好 | 低（需 undo_log 表） | 通用业务场景（默认模式） |
| **TCC** | 业务层实现 Try / Confirm / Cancel | 最终一致 | 好 | 高（需手写三方法） | 对资源预留有强需求的场景 |
| **Saga** | 正向编排 + 反向补偿，无锁 | 最终一致 | 好 | 中 | 长事务、跨系统调用 |

---

## 二、XA 模式

### 原理

基于数据库原生 XA 协议。RM（资源管理器）一阶段执行 SQL 但**不提交**，等 TM（事务管理器）二阶段统一下达 commit 或 rollback。

```
TM (Seata)
  │
  ├── 一阶段: 通知所有 RM 执行 SQL，不提交，持锁
  │
  ├── 二阶段:
  │     ├── 全部成功 → commit
  │     └── 任一失败 → rollback
  │
  ▼
RM (MySQL/Oracle) 原生 XA 回滚
```

### 特点

- 强一致，数据绝不丢
- RM 持锁贯穿整个事务，并发性能最差
- 依赖数据库支持 XA 协议

## 三、AT 模式（默认）

### 原理

一阶段**直接提交**，同时记录 undo_log（反向 SQL）。二阶段需要回滚时执行反向 SQL 补偿。

```
一阶段:
  UPDATE account SET money = money - 100 WHERE id = 1  → 直接提交
  记录 undo_log: UPDATE account SET money = money + 100 WHERE id = 1

二阶段:
  成功 → 删 undo_log
  失败 → 执行 undo_log 中的反向 SQL
```

### 脏写问题与全局锁

```
事务A: 扣款 100，一阶段提交（行锁释放）
事务B: 读到余额 900，也扣款 100 ← 脏读！
事务A: 二阶段回滚，余额恢复 1000 → 事务B 读到的 900 是错的

解决: 全局锁
  事务A 一阶段提交前 → Seata 记录全局锁（表 + 主键）
  事务B 更新同一行 → 检查全局锁 → 有锁则等待 → 避免脏写
```

### 写隔离

对修改过的记录加全局锁，其他事务更新前必须检查，防止写冲突。

### AT vs XA

| | XA | AT |
|---|---|---|
| 一阶段 | 不提交 | 直接提交 |
| 回滚方式 | 数据库原生回滚 | 反向 SQL 补偿 |
| 锁 | 数据库行 | 行锁一阶段后释放，加全局锁 |
| 性能 | 差（长锁） | 好（短锁） |
| 侵入 | 无 | 需 undo_log 表 |

## 四、TCC 模式

### 原理

业务层手动实现三个方法：

| 方法 | 作用 | 时机 |
|---|---|---|
| **Try** | 预留资源 + 检查 | 一阶段 |
| **Confirm** | 确认执行 | 二阶段（全部 Try 成功） |
| **Cancel** | 释放预留资源 | 二阶段（有 Try 失败） |

### 两个特殊问题

#### 空回滚

```
Try 阶段网络超时 → TM 认为 Try 失败 → 发 Cancel
但 Try 实际没有执行（未预留任何资源）
Cancel 执行时发现没有资源可释放 → 返回成功，就是空回滚

解决: Cancel 方法判断 Try 是否执行过，没执行过直接 return success
```

#### 业务悬挂

```
Try 超时 → TM 发 Cancel → Cancel 先到并执行
然后 Try 请求慢悠悠到达 → Try 执行成功，预留了资源
但此时没有后续 Confirm/Cancel 来释放 → 资源永远挂在那

解决: Try 方法执行前检查是否已经 Cancel 过，是则拒绝执行
```

## 五、Saga 模式

### 原理

长事务拆分多个步骤，正向顺序执行，失败时逆序补偿。

```
正向: Step1 → Step2 → Step3 → Step4
                        ↓ 失败
补偿:               ← Compensate3 ← Compensate2 ← Compensate1
```

### 特点

- 无锁，不保证隔离性
- 补偿逻辑需手写
- 适合长流程（跨境转账、多日审批、跨系统对接）

---

## 六、选型建议

| 场景 | 推荐模式 | 原因 |
|---|---|---|
| 通用业务、一致性要求不高 | **AT** | 默认模式，低侵入，性能好 |
| 金融核心链路、强一致要求 | **XA** | 强一致，依赖数据库原生回滚 |
| 需业务层资源预留 | **TCC** | 灵活控制，改造量大 |
| 长事务、跨系统 | **Saga** | 无锁，异步补偿 |

---

## 七、面试口述

> "Seata 有四种模式。AT 是默认模式，一阶段直接提交同时记 undo_log，二阶段失败执行反向 SQL，通过全局锁解决脏写。XA 基于数据库 XA 协议，两阶段提交，强一致但持锁长性能差。TCC 是业务层手写 Try/Confirm/Cancel，需要处理空回滚和悬挂。Saga 是长事务正向编排 + 反向补偿，无锁适合跨系统流程。
>
> 一般业务用 AT，金融强一致用 XA，需要精细控制资源用 TCC，长跨流程用 Saga。"
