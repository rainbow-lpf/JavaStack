## 第一章：为什么需要分布式事务？

### 1.1 从单体到微服务，事务变了

```
单体时代:
  @Transactional
  public void order() {
      orderDao.insert();    // 本地事务
      accountDao.deduct();  // 同一个数据库，同一个事务
      stockDao.reduce();    // 出问题一起回滚
  }
  → 一个 @Transactional 搞定

微服务时代:
  public void order() {
      orderService.create();     // 订单服务，数据库A
      accountService.deduct();   // 账户服务，数据库B
      stockService.reduce();     // 库存服务，数据库C
  }
  → 三个独立的数据库，各自的本地事务互不感知
  → 订单创建成功，账户扣款失败 → 数据不一致！
```

### 1.2 具体问题

```
步骤1: 订单服务创建订单 → 成功 (数据库A提交)
步骤2: 账户服务扣款 → 失败! (数据库B回滚)
结果: 订单已经创建了，钱没扣 → 白送商品

如果反过来:
步骤1: 账户服务扣款 → 成功 (数据库B提交)
步骤2: 订单服务创建订单 → 失败! (数据库A回滚)
结果: 钱扣了，订单没创建 → 用户投诉
```

**这就是分布式事务要解决的问题：跨多个服务/数据库的操作，要么全部成功，要么全部失败。**

## 第二章：Seata 是什么？

Seata = Simple Extensible Autonomous Transaction Architecture

三大角色：

```
┌──────────────┐
│  TC (Server) │  ← 事务协调者，单独部署的 Seata Server
│  管理全局事务  │
│  协调分支提交  │
└──────┬───────┘
       │
  ┌────┴────┐
  │         │
  ▼         ▼
┌─────┐  ┌─────┐
│ TM  │  │ RM  │  ← 嵌在微服务里的
└─────┘  └─────┘
```

| 角色 | 全称 | 在哪 | 职责 |
|---|---|---|---|
| **TC** | Transaction Coordinator | Seata Server（独立部署） | 维护全局事务状态，协调提交/回滚 |
| **TM** | Transaction Manager | 业务发起方微服务 | 开启全局事务，最终决定 commit 还是 rollback |
| **RM** | Resource Manager | 参与方微服务 | 管理本地资源（数据库），报告分支状态，执行提交/回滚 |

## 第三章：四种模式概览

| 模式 | 一句话 | 一致性 | 性能 | 你需要做什么 |
|---|---|---|---|---|
| **XA** | 让数据库自己管，锁住等通知 | 强一致 | 差 | 不需要写代码 |
| **AT** | 自动记反向 SQL，失败了倒着执行一遍 | 最终一致 | 好 | 表里加 undo_log 表 |
| **TCC** | 你自己写 Try / Confirm / Cancel | 最终一致 | 好 | 写三套代码 |
| **Saga** | 按顺序执行步骤，失败从后往前补偿 | 最终一致 | 好 | 写正向 + 补偿代码 |

## 第四章：XA 模式 —— 最老实的方案

### 4.1 大白话

> 你跟小组三个人说："我数 3、2、1，一起调接口，先别提交。等我确认没问题，说'提交'，你们再提交。有一个人调失败，我说'回滚'，你们就都回滚。"

### 4.2 流程

```
TM                    TC                  RM(订单)        RM(账户)       RM(库存)
 │                     │                     │              │              │
 │── 开启全局事务 ────►│                     │              │              │
 │                     │                     │              │              │
 │                     │──── 执行SQL，别提交 ─►│              │              │
 │                     │                     │ 执行，返回OK  │              │
 │                     │                     │ (但未提交!)   │              │
 │                     │                     │              │              │
 │                     │────────── 执行SQL，别提交 ──────────►│              │
 │                     │                     │              │ 执行，返回OK  │
 │                     │                     │              │ (但未提交!)   │
 │                     │                     │              │              │
 │                     │────────────────────── 执行SQL，别提交 ────────────►│
 │                     │                     │              │              │ 执行，返回OK
 │                     │                     │              │              │ (但未提交!)
 │                     │                     │              │              │
 │── 全部OK，Commit ──►│                     │              │              │
 │                     │── 提交! ───────────►│ 提交         │              │
 │                     │── 提交! ──────────────┼───────────►│ 提交         │
 │                     │── 提交! ───────────────────────────┼─────────────►│ 提交
```

### 4.3 特点

- 一阶段执行 SQL 但**不提交**，锁一直不释放
- 二阶段 TM 通知 TC，TC 通知所有 RM：全部 OK 就提交，有一个失败就回滚
- 回滚由数据库原生机制完成，不需要写任何补偿代码
- **最大的问题：锁持有太久**，事务整个过程都锁着数据库行

## 第五章：AT 模式 —— Seata 默认模式（最常用）

### 5.1 大白话

> XA 说"先别提交，等大家都好了再说"。AT 说"不用等，你先提交，我帮你记下你改了什么。万一回头要反悔，我帮你反向操作回去。"

### 5.2 核心思路

```
一阶段:
  执行业务SQL → 直接提交（释放本地锁）
  同时记录反向SQL到 undo_log 表

二阶段:
  全部成功 → 删掉 undo_log
  有失败   → 执行 undo_log 里的反向SQL → 删掉 undo_log
```

### 5.3 一个具体的例子

```
场景: 下单扣库存，账户余额 1000，扣 100

一阶段:
  -- 业务SQL
  UPDATE account SET balance = balance - 100 WHERE id = 1
  -- 提交! 余额变成 900

  -- 自动记录反向SQL到 undo_log 表
  INSERT INTO undo_log VALUES (
      'UPDATE account SET balance = balance + 100 WHERE id = 1'
  )

二阶段-回滚:
  -- 执行反向SQL
  UPDATE account SET balance = balance + 100 WHERE id = 1
  -- 余额恢复 1000
  -- 删掉这条 undo_log
```

### 5.4 脏写问题 —— AT 模式最大的坑

```
事务A: UPDATE account SET balance = 900  (一阶段提交，锁释放)
                                            │
事务 SELECT balance → 拿到 900              │    ← 并发! 
事务B: UPDATE balance = 800 (在 900 基础上扣)  │
                                            │
事务A: 二阶段回滚，执行反向SQL                  │
       UPDATE account SET balance = 1000       │    ← 把事务B的结果覆盖了！
                                            │
最终: balance = 1000                          │    ← 事务B 白干了
```

**Seata 的解决方案：全局锁**

```
事务A 一阶段提交前 → 向 TC 申请全局锁: account表#id=1
事务B 更新同一行时 → 检查全局锁 → 发现被事务A锁住了 → 等待或报错
事务A 二阶段完成 → 释放全局锁
事务B 拿到锁 → 继续执行
```

全局锁存在 TC（Seata Server）内存中，不依赖数据库。

### 5.5 写隔离 —— 保守做法

```
对于有全局锁的记录:
  事务B 读 → 可以读（因为A已经提交了，读是正常的）
  事务B 写 → 必须拿到全局锁，否则等待

  如果A最终回滚: B的写被全局锁拦住了，不会产生脏写
  如果A最终提交: B拿到锁后继续写，顺序正确
```

### 5.6 为什么 AT 比 XA 快

```
XA:
  一阶段执行SQL(持锁) → 等TM通知 → 二阶段提交(释放锁)
  └────────────── 全程持锁 ──────────────┘

AT:
  一阶段执行SQL → 提交(释放锁！) → 记录undo_log
  └── 持锁极短 ──┘
  二阶段需要回滚时: 拿全局锁 → 执行反向SQL → 释放全局锁
  └── 只在回滚时短暂持锁 ──────────────┘
```

AT 的锁只在一阶段提交的瞬间持有，XA 的锁贯穿整个事务。所以 AT 并发性能远好于 XA。

## 第六章：TCC 模式 —— 业务层自己控制

### 6.1 大白话

> AT 是框架帮你自动生成反向 SQL，TCC 是"你自己写反向逻辑，因为你最懂你的业务"。

### 6.2 三个方法

| 方法 | 作用 | 举例（扣钱） |
|---|---|---|
| **Try** | 预留资源，做检查 | 冻结 100 元（余额不减，冻结字段+100） |
| **Confirm** | 确定执行 | 冻结的 100 → 真正扣掉 |
| **Cancel** | 释放资源 | 冻结的 100 → 解冻，恢复可用 |

### 6.3 为什么用 TCC，而不是 AT？

AT 的场景：一条 UPDATE SQL → 反向 SQL 就是 UPDATE 回去，简单。

TCC 的场景：

```
你不是改数据库，你是：
  - 调第三方支付接口（没有反向 SQL 这种说法）
  - 发短信/邮件/推送
  - 操作 Redis 缓存
  - 调其他微服务（不是数据库操作）

这些操作没有"反向 SQL"，必须你自己写补偿逻辑。
```

### 6.4 空回滚和业务悬挂

这两个问题在网上很难理解，换个角度讲：

#### 空回滚：Cancel 到了，Try 还没执行

```
TM 发起 Try → 网络超时！TM 以为失败了 → 发 Cancel
Cancel 先到 → 执行 Cancel，但资源根本没预留，怎么解冻？
```

**解决：** Cancel 里判断"有没有 Try 的记录"，没有就直接返回成功。

#### 业务悬挂：Try 到的太晚

```
TM 发起 Try → 网络卡了 → TM 等不及了 → 发 Cancel → Cancel 执行完了
                                                         │
                                    Try 这时候才慢悠悠到达 ←┘
                                    Try 执行，预留了资源
                                    但是没人来 Confirm 或 Cancel 了！
                                    资源永远冻结在那
```

**解决：** Try 执行前检查"是不是已经 Cancel 过了"，是则拒绝。

## 第七章：Saga 模式 —— 长事务专属

### 7.1 大白话

> 不是两步操作，是有 10 个步骤的流程（比如出差审批：申请 → 主管批 → 经理批 → 财务批 → 订机票 → 订酒店...），每一步成功了往前走，某一步失败了从最后一步往前取消。

### 7.2 流程

```
正向步骤: Step1 → Step2 → Step3 → Step4 → Step5
                                           ↓ 失败
补偿步骤:                            Cancel4 → Cancel3 → Cancel2 → Cancel1
```

### 7.3 特点

- 无锁。每步都独立提交，不需要等待
- 不保证隔离性。Step3 的中间结果，外部服务可能已经看到了
- 适合：流程特别长、跨多个系统、不需要强隔离的场景
- 每一步的补偿代码需要手写

## 第八章：四种模式完整对比

| | XA | AT | TCC | Saga |
|---|---|---|---|---|
| **一句话** | 数据库自己锁住等通知 | 先提交，失败反向SQL补偿 | 自己写Try/Confirm/Cancel | 顺序执行，失败逆序补偿 |
| **一阶段** | 执行不提交，持锁 | 提交，记undo_log | Try（预留资源） | 业务执行，直接提交 |
| **二阶段** | TC通知提交/回滚 | 执行反向SQL/删undo_log | Confirm/Cancel | 逆序执行补偿 |
| **回滚** | 数据库原生 | 反向SQL | Cancel方法 | 补偿方法 |
| **锁** | 数据库行锁（长） | 一阶段后释放，全局锁（短） | 无数据库锁 | 无锁 |
| **性能** | 差 | 好 | 好 | 好 |
| **一致性** | 强一致 | 最终一致 | 最终一致 | 最终一致 |
| **代码侵入** | 无 | undo_log表 | 高（三套代码） | 中（正向+补偿） |
| **适用场景** | 强一致的金融操作 | 通用业务（默认） | 有非DB资源需补偿 | 长事务/跨系统流程 |

## 第九章：选哪种？

```
你的操作全是数据库操作？
  └─ 是 → 用 AT（不用多写，加张 undo_log 表就行）
  └─ 否 → 下一步

你对一致性要求极高（钱相关的核心操作）？
  └─ 是 → 用 XA（虽然慢，但数据绝对不出错）
  └─ 否 → 下一步

你的操作里有调第三方接口、发短信、改缓存？
  └─ 是 → 用 TCC（你自己写补偿逻辑，因为你最懂业务）
  └─ 否 → 下一步

你的业务流程特别长，有 5 步以上，跨多个系统？
  └─ 是 → 用 Saga（无锁，异步补偿，不卡流程）
```

## 第十章：面试口述总结

> "Seata 解决微服务下跨库操作的一致性问题。四个模式：
>
> XA 最老实——让数据库锁住等通知，强一致，但持锁太长性能差；
>
> AT 最聪明——先提交，同时记反向 SQL，失败了倒着执行一遍，通过全局锁防止脏写。比 XA 快很多，是默认模式；
>
> TCC 最灵活——你自己写 Try 预留资源、Confirm 确认、Cancel 释放。适合有非数据库资源（调第三方、发消息）的场景，需要处理空回滚和业务悬挂；
>
> Saga 最佛系——适合长流程，每步独立提交，失败了从后往前补偿。无锁，但不保证隔离性。
>
> 一般项目 AT 够用了，金融强一致用 XA，复杂资源操作用 TCC，长流程用 Saga。"
