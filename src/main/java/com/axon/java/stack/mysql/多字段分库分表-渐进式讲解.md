# 多字段分库分表：渐进式讲解

> 一张物理表只有一个路由算法、一个分片键。那 `userId`、`orderId`、`merchantId` 多个字段都要查，到底怎么分？
> 七层递进，从"选一个键"到"组合分片键"，彻底吃透。

---

## 第一层：先搞懂"分片键"是什么

分库分表的本质：**一条数据该落到哪张表，由路由算法算出来。**

```
路由算法：分片键取值 → hash / 取模 / 范围 → 确定物理分片

userId = 9527
   │
   ▼
9527 % 8 = 3
   │
   ▼
落到 user_3 表
```

**关键事实：一个表，只能有一个分片键、一套路由算法。**

> 这是物理约束，不是配置问题。一旦你按 `orderId % 8` 分，那 `WHERE userId = ?` 这条 SQL 里就没有分片键，MySQL 中间件不知道去哪张表找，只能**每张表都发一遍**。

---

## 第二层：多字段查询的矛盾点

订单表 `t_order` 有这些查询场景：

| 查询场景 | 分片键 = userId | 分片键 = orderId |
|---------|:---:|:---:|
| `WHERE userId = ?` | ✅ 单分片 | ❌ 全分片广播 |
| `WHERE orderId = ?` | ❌ 全分片广播 | ✅ 单分片 |
| `WHERE merchantId = ?` | ❌ 广播 | ❌ 广播 |
| `WHERE status = 'PAID'`（运营查） | ❌ 广播 | ❌ 广播 |

**结论：没有完美的单分片键。多字段分表的本质 = "一主多辅"——主键选最高频维度精确路由，其余维度用辅助方案补。**

```
维度按查询 QPS 排序：
  第 1 高频维度  →  主分片键（精确路由）
  第 2 高频维度  →  基因法 / 异构索引表
  第 3+ 维度     →  异构索引表 / ES
  低频后台查询  →  ES / 广播兜底
```

---

## 第三层：方案一——基因法（最经典，面试必讲）

### 3.1 核心思想

**把 A 键的"基因"嵌进 B 键里**，让 B 键自带 A 键的路由信息。这样一份数据、零冗余，两个键都能精确路由。

### 3.2 原理

```
雪花算法原始结构：
┌──────────────┬──────────┬────────────┐
│ 41位 时间戳  │ 10位 机器 │ 12位 序列  │
└──────────────┴──────────┴────────────┘

基因法改造（把机器 ID 段换成 userId 的基因）：
┌──────────────┬────────────────┬────────────┐
│ 41位 时间戳  │ userId 低8位基因 │ 12位 序列  │
└──────────────┴────────────────┴────────────┘
                      ↑
              生成 orderId 时嵌入 userId % 256
```

分表 256 张（2^8）：

```
按 orderId 查：orderId % 256 = 基因位 = 直接路由 ✅
按 userId  查：userId  % 256 = 同一片（orderId 里嵌的就是它）✅
```

### 3.3 伪代码

```
// 生成订单 ID（序列号左移 k 位让位，低 k 位填基因）
long gene    = userId & 0xFF;              // 取 userId 低 8 位
long orderId = (time << 22) | (worker << 12) | (seq << 8) | gene;

// 按 orderId 查：orderId % 256  → 路由
// 按 userId  查：userId  % 256  → 路由
// 两条路径算出的分片号一定相同
```

> ⚠️ 注意：必须让序列号左移 8 位、低 8 位固定填基因，不能直接替换低 8 位（否则同毫秒 seq=0 和 seq=1 会生成相同 ID）。详见 `基因法-渐进式讲解.md`。

### 3.4 优缺点

| 优点 | 缺点 |
|------|------|
| 一份数据、零冗余、强一致 | 基因位数决定分片数上限（8 位 → 最多 256 片） |
| SQL 无感知，不改查询逻辑 | ID 生成器要自己改造 |
| 无二次查询开销 | **只能救一个维度**（两个基因就挤爆位数） |

> 一句话：**基因法 = 用 ID 的冗余位数，换第二个维度的精确路由。本质是空间换路由能力。**

## 第四层：方案二——异构索引表（空间换时间）

### 4.1 核心思想

**同一份数据，按不同分片键各存一份**。主表管交易，异构表管别的查询维度。

```
订单主表 t_order           → 按 userId 分 8 片（买家维度，最高频）
订单异构表 t_order_seller  → 按 merchantId 分片（商家维度）

商家查"我的订单"：
  SELECT user_id, order_id FROM t_order_seller WHERE merchantId = ?  → 精确路由 ✅
  拿到 (user_id, order_id) 列表 → 按 userId 路由回主表批量取详情
```

### 4.2 异构表只做"索引"

**实战要点：异构表通常只存索引字段 + 主表分片键，很薄。**

```sql
-- 异构表：维度键 + 主表分片键(user_id) + 行定位键(order_id)
CREATE TABLE t_order_seller (
  merchant_id BIGINT NOT NULL,
  user_id     BIGINT NOT NULL,   -- 主表按 user_id 分片，回表路由靠它
  order_id    BIGINT NOT NULL,   -- 到片后定位具体行
  PRIMARY KEY (merchant_id, order_id)
) -- 按 merchant_id 分片
```

查到 (user_id, order_id) 列表，按 `user_id` 路由回主表各片，再 `WHERE order_id IN (...)` 定位行。

> **关键：异构表必须存主表的分片键（这里 user_id）**，否则回主表无法路由，只能全分片广播。主键放维度键 + 定位键，user_id 作为普通字段存即可。

### 4.3 数据同步两种方式

```
方式 1：双写
  写主表 + 写异构表，本地事务 / 事务消息保证一致
  优点：实时、可控
  缺点：写放大、业务代码侵入

方式 2：binlog
  写主表 + Canal 监听 binlog 异步写异构表
  优点：业务无感知、解耦
  缺点：最终一致（毫秒级延迟）、多一套同步链路
```

### 4.4 优缺点

| 优点 | 缺点 |
|------|------|
| 各维度查询都精确路由 | 存储翻倍 |
| 维度数量不限，加维度加表 | 一致性从强变最终 |
| 异构表很薄，成本低 | 写放大 |

## 第五层：方案三——外置索引（ES / 映射表）

### 5.1 核心思想

**非分片键的复杂查询，先查外部索引拿分片键，再精确路由回库。**

```
运营后台按 status='PAID' 查订单：
  ① 查 ES（订单宽表，binlog 同步）
     → 拿到 orderId + userId 列表
  ② 拿 userId % 256 路由回 MySQL 批量取详情 ✅
```

### 5.2 为什么适合运营/后台

```
核心交易链路不依赖 ES：
  ES 挂了 → 只影响后台查询，不影响下单
  下单走 userId / orderId 精确路由，不碰 ES
```

### 5.3 优缺点

| 优点 | 缺点 |
|------|------|
| 任意维度任意组合查询 | 引入 ES 运维成本 |
| 顺带解决复杂搜索、深度分页 | 一致性靠同步链路 |

---

## 第六层：方案四——广播查询（兜底，尽量别用）

不带分片键 → 中间件广播到所有分片 → 流式归并。

```
适用：分片少、数据量小、低频查询
问题：N 片 = N 倍数据库压力 + 归并内存压力
      深度分页雪上加霜（每片都要排序取前 N 再全局归并）
```

> **广播是"实在没办法"的兜底，不是设计目标。** 一个查询如果高频广播，说明分片键选错了。

## 第七层：真正的"多字段"——组合分片键

前面都在讲"一个主键 + 辅助方案"。还有一种字面意义的**多字段分表：组合分片键（复合分片）**。

### 7.1 核心思想

**路由算法同时吃多个字段**，`(a, b)` 组合决定落到哪张表。

```
组合分片键 = (userId, orderId)
路由算法：hash(userId, orderId) % 8
```

### 7.2 什么时候用

| 场景 | 说明 |
|------|------|
| 字段总是**成对出现** | 如 `(租户 tenantId, 业务 bizId)`，所有 SQL 都同时带两个条件 |
| 避免单键数据倾斜 | 单个键分布不均，组合后打散 |
| 复合主键的场景 | 如 `(buyer_id, seller_id)` 都参与路由 |

### 7.3 致命陷阱：不是"两个都能单独查"

```
组合分片键 (a, b)：
  WHERE a = ? AND b = ?   → ✅ 精确路由（两个键都有）
  WHERE a = ?             → ❌ 广播！缺了 b，路由算不出来
  WHERE b = ?             → ❌ 广播！缺了 a

组合分片键 ≠ 两个字段都能单独精确路由
组合分片键 = 只有"成对出现"时才能精确路由
```

**所以：组合分片键只适合"字段永远成对出现"的场景，比如多租户系统里 `tenantId + bizId` 永远一起查。**

### 7.4 组合分片键 vs 基因法

| | 组合分片键 | 基因法 |
|------|------|------|
| 路由方式 | 两个键一起 hash | 键 B 里嵌键 A 的基因 |
| `WHERE a=?` 单独查 | ❌ 广播 | ✅ 精确 |
| `WHERE b=?` 单独查 | ❌ 广播 | ✅ 精确 |
| 适用 | 字段成对出现 | 两键都可能单独查 |

> 一句话：**组合分片键解决"数据打散"，基因法解决"多键各自精确路由"，两者目的不同。**

## 实战：ShardingSphere 配置示例

### 基因法落地（复合分片算法）

```yaml
# application.yml
spring:
  shardingsphere:
    rules:
      sharding:
        tables:
          t_order:
            # 按 orderId 和 userId 都能路由（基因法）
            actual-data-nodes: ds0.t_order_$->{0..255}
            database-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: order-alg
            key-generate-strategy:
              column: order_id
              key-generator-name: gene-snowflake
        sharding-algorithms:
          order-alg:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 256}
        key-generators:
          gene-snowflake:
            type: SNOWFLAKE  # 自定义改造：序列段嵌入 userId 低 8 位
```

### 异构表落地（绑定表 + 广播表）

```yaml
spring:
  shardingsphere:
    rules:
      sharding:
        tables:
          t_order:
            actual-data-nodes: ds0.t_order_$->{0..7}
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: user-mod
          t_order_seller:
            actual-data-nodes: ds0.t_order_seller_$->{0..7}
            table-strategy:
              standard:
                sharding-column: merchant_id
                sharding-algorithm-name: merchant-mod
        sharding-algorithms:
          user-mod:
            type: MOD
            props:
              sharding-count: 8
          merchant-mod:
            type: MOD
            props:
              sharding-count: 8
```

## 选型决策树

```
多个字段都要查 ↓
  第 1 问：哪个维度 QPS 最高？
    → 选它做主分片键

  第 2 问：第二高频维度能改造 ID 生成器吗？
    → 能 → 基因法（成本最低，零冗余）
    → 不能 → 异构索引表

  第 3 问：还有第三、四个维度？
    → 异构索引表（薄索引 + 回主表）

  第 4 问：有没有复杂搜索 / 聚合 / 后台查询？
    → ES 外置索引

  第 5 问：以上都不想建？
    → 广播兜底（确认分片数少、数据量小）
```

**核心思想：按查询频率分配成本——越高频的维度越要精确路由，越低频的越可容忍二次查询或异步索引。**

---

## 一句话总结

```
单分片键选最高频维度 → 第二维度用基因法（ID 嵌基因，两键同片）
→ 更多维度用异构索引表（薄索引回表）→ 复杂查询丢 ES → 广播兜底。
多字段分表不是"选一个字段"，而是"一主多辅，按频率分配成本"。
```

## 面试话术（30 秒）

> 一张物理表只有一个路由算法，多字段查询的本质是"一主多辅"：主分片键选最高频维度；第二维度用基因法——把用户 id 的低位嵌入订单 id 的生成逻辑，两个键取模同片，零冗余强一致；再多的维度用异构索引表，binlog 异步同步一份薄索引（只存维度 + 主键）再回主表；运营后台的复杂查询丢给 ES。至于字面意义的组合分片键，只适合字段永远成对出现的场景（如多租户 tenantId + bizId），因为组合键只有成对出现才能精确路由，拆开单独查还是广播。
