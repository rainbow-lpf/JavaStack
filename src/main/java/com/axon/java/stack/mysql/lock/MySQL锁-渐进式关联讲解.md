# MySQL 锁：从零到精通（渐进式关联讲解）

> 从"为什么需要锁"开始，一环扣一环推进。读完本文你能在面试时清楚讲出**每种锁出现的背景、解决的问题、以及它们之间怎么联动**。

---

## 第一层：没有任何锁的世界 → 引出"锁"这个概念

假设数据库没有任何锁，两个用户同时操作同一条数据：

```
用户 A：账户余额 1000 → 取出 500 → 余额变 500
用户 B：账户余额 1000 → 取出 800 → 余额变 200

时间线：
T1: A 读到余额 1000
T2: B 读到余额 1000
T3: A 写入 500
T4: B 写入 200  ← 把 A 的结果覆盖了！
```

**问题：更新丢失。** 根本原因：两个操作"不知对方存在"，同时读同时写。

**解：锁。** 一个人操作时，另一个人等着。这就是锁最原始的需求——**互斥**。

> **第一层悟道：锁 = 互斥访问 = 一个人改，别人排队。**

---

## 第二层：表锁 → 粗暴但好用

最直接的锁法：谁在用这张表，整张表都锁住。

```
表锁 = 把整张表锁起来
┌──────────────────┐
│   user 表（锁）    │  ← 表上有锁
│ id  name  balance │
│ 1   张三  500     │
│ 2   李四  800     │
└──────────────────┘
  ↑ Session1 在操作时，Session2 等着
```

### 两种表锁

| 锁类型 | 持有者能做什么 | 别人能做什么 |
|------|------|------|
| **读锁（共享锁）** | 读 | 别人也能读，但不能写 |
| **写锁（排他锁）** | 读写都行 | 别人读/写都不行，等着 |

**问题来了：** 表锁太粗了。我只想改张三那一行，为什么李四那行也锁了？并发能力差。

> **第二层悟道：表锁简单粗暴，但粒度太大 → 需要更细的锁。**

---

## 第三层：行锁 → 精细到每一行

InnoDB 支持行锁：只锁 WHERE 条件命中的行。张三改张三的，李四动李四的，互不干扰。

```
行锁 = 只锁特定行
┌──────────────────┐
│ id=1 张三 500 ← 锁 │
│ id=2 李四 800    │  ← 这行没锁，可以同时操作
│ id=3 王五 1000   │
└──────────────────┘
```

```sql
-- Session1
UPDATE user SET balance=500 WHERE id=1;  -- 锁 id=1 这一行

-- Session2
UPDATE user SET balance=900 WHERE id=2;  -- 不阻塞！锁的是不同行
```

**新问题：** MySQL 怎么知道锁哪些行？靠索引！WHERE 条件走索引 → 精确锁行。没索引 → 全表扫描 → 每行都锁 → 退化成表锁。

> **第三层悟道：行锁靠索引，没索引 = 行锁退化为表锁。索引是行锁的"眼睛"。**

---

## 第四层：读锁(S) 和写锁(X) → 锁的模式

行锁也有两种模式：

```
S：共享锁，读的时候加，别人也能读
X 锁：排他锁，写的时候加，别人什么都不能干
```

```
兼容矩阵：
         想加 S 锁   想加 X 锁
已有 S 锁    ✅        ❌
已有 X 锁    ❌        ❌
```

```sql
-- S 锁
SELECT * FROM user WHERE id=1 LOCK IN SHARE MODE;

-- X 锁
SELECT * FROM user WHERE id=1 FOR UPDATE;
UPDATE user SET name='xx' WHERE id=1;  -- 自动加 X 锁
```

**此刻的疑问：** 上面说 `SELECT * FROM user WHERE id=1` 不加锁，那 Session1 写这行、Session2 读这行，读到的值是什么？读旧值还是被阻塞？

答：**读不加锁，直接读旧版本。** InnoDB 有 MVCC（多版本并发控制），写不阻塞读。但这是后话，先继续讲锁。

> **第四层悟道：S 锁共享，X 锁独占。但普通 SELECT 根本不加 S 锁（靠 MVCC 读快照），只有 LOCK IN SHARE MODE 才手动加 S 锁。**

## 第五层：意向锁 → 表锁和行锁的桥梁

现在有了表锁和行锁，出现新问题：

```
场景：
  事务 A 把 id=3 加 X 行锁
  事务 B 想加整个表的 X 表锁（如 LOCK TABLE user WRITE）

事务 B 怎么知道表里有没有行被锁？
  办法 1：逐行检查 → 太慢
  办法 2：表上有标记 → 意向锁！
```

**意向锁就是一种表级标记，表示"这个表里某些行正在被锁着"：**

```
事务 A 加行 X 锁之前：
  ① 先在表上加 IX 锁（意向排他锁，Intention X）
  ② 再加行 X 锁

事务 B 要加表 X 锁时：
  ① 检查表上有没有 IX 锁
  ② 有 → 说明表里有行被锁 → 阻塞等待
```

```
兼容矩阵：
        IS   IX    S    X（表锁）
  IS    ✅   ✅   ✅   ❌
  IX    ✅   ✅   ❌   ❌
  S     ✅   ❌   ✅   ❌
  X     ❌   ❌   ❌   ❌
```

**关键理解：意向锁之间不互斥。** IS 和 IX 都只是"打算"，不是真的锁数据。IS + IX 可以共存，因为多个事务各自锁自己的行，不冲突。

> **第五层悟道：意向锁 = 表级"路标"。行锁上车前在路口插旗，表锁一来先看有没有旗。不必逐行检查，一眼就知。**

## 第六层：间隙锁(Gap Lock) → 防幻读

行锁只能锁住**已经存在的行**，锁不住"不存在"的行。

```
表中数据：id = 5, 10, 15

Session1: SELECT * FROM t WHERE id BETWEEN 5 AND 15 FOR UPDATE;
  → 锁住 id=5, id=10, id=15 这三行

Session2: INSERT INTO t (id) VALUES (7);
  → id=7 的行还不存在，行锁锁不住它
  → 插入成功！
  → Session1 再查一次 → 多了一行 → 幻读！
```

**解决：锁住"间隙"——记录之间的空隙。**

```
表中数据：  [5]  ──间隙──  [10]  ──间隙──  [15]
               ↑            ↑
          锁住 (-∞,5]   锁住 (5,10]
          (10,15]    (15,+∞) 也被锁住（按查询范围）

锁住的不仅是 5、10、15 这三条记录，还有它们之间的所有空隙。
id=7 在 (5,10) 间隙中 → 插入被阻塞 → 幻读解决！
```

> **第六层悟道：行锁锁"有"，间隙锁锁"无"。行锁只锁已有记录，别人可以插入新行 → 幻读。间隙锁把"空的也锁住"→ 幻读终结。**

## 第七层：Next-Key Lock → RR 级别默认算法

现在你有了：
- **Record Lock**：锁已有记录
- **Gap Lock**：锁记录间空隙

把两者合并 → **Next-Key Lock**。它是 InnoDB 在 RR 隔离级别下的默认行锁算法。

```
Next-Key Lock = Record Lock + Gap Lock

表中数据： [5]  [10]  [15]

Next-Key Lock 锁住的范围：
  (-∞, 5]   = 负无穷到5的空隙 + 5这条记录
  (5, 10]   = 5到10的空隙 + 10这条记录
  (10, 15]  = 10到15的空隙 + 15这条记录
  (15, +∞)  = 15之后的所有空袭（只有Gap，无右边记录）
```

```
为什么叫 Next-Key？
  锁 = 左开右闭区间 (a, b]
  key = 索引值 = 右边的记录
  Next-Key = 从当前记录到"下一个key"之间的区间
```

**一句话：** Next-Key Lock 既锁记录又锁间隙，别人不能改已有记录，也不能插入新记录 → 幻读彻底解决。

> **第七层悟道：Record Lock + Gap Lock = Next-Key Lock。InnoDB RR 级别下默认就是这个。一条锁同时干两件事：堵修改 + 堵插入。**

## 第八层：插入意向锁(Insert Intention Lock) → 优化并发插入

间隙锁有问题：锁了 (5,10) 整个区间，所有插入都被阻塞。

```
Session1: SELECT ... WHERE id BETWEEN 5 AND 15 FOR UPDATE;
  → 锁住 (5,10) 间隙

Session2: INSERT INTO t VALUES (7);   → 阻塞
Session3: INSERT INTO t VALUES (8);   → 阻塞
```

但 Session2 和 Session3 插入的位置不同（id=7 和 id=8），应该可以并发才对。

**插入意向锁登场：** 事务插入前在间隙上加一个"插入意向锁"。它与 Gap Lock 互斥，但**多个插入意向锁之间兼容**。

```
Session2: INSERT id=7 → 加 (5,10) 的插入意向锁
Session3: INSERT id=8 → 也加 (5,10) 的插入意向锁

如果 Session1 没有持有 Gap Lock：
  Session2 和 Session3 互相不阻塞！✅ 并发插入！

如果 Session1 持有 Gap Lock：
  Session2 和 Session3 的插入意向锁被阻塞
```

> **第八层悟道：插入意向锁 = 间隙锁的"并发优化版"。同一个间隙的不同位置可以同时插入。但只对插入意向锁之间兼容，跟 Gap Lock 不兼容。**

## 第九层：AUTO-INC 锁（自增锁）→ 主键自增的并发保障

```sql
CREATE TABLE t (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(20));
```

两个事务同时 INSERT，id 不能重复。怎么保证？

```
AUTO-INC 锁：
  事务 A 拿到自增值 1 → 释放
  事务 B 拿到自增值 2 → 释放
  ......
  互不干扰，值连续
```

**轻量级 vs 重量级：**

```
innodb_autoinc_lock_mode = 0（传统）：
  事务 INSERT 期间持有表级锁 → 值连续但并发差

innodb_autoinc_lock_mode = 1（默认）：
  INSERT 几条已知 → 用轻量级互斥锁（拿完值就释放）
  INSERT...SELECT 未知 → 用表级 AUTO-INC 锁

innodb_autoinc_lock_mode = 2（交错）：
  全部轻量级 → 并发最好，但值可能不连续（有间隙）
```

> **第九层悟道：AUTO-INC 锁让自增主键在并发下不重复。默认模式 1 兼顾连续性和并发性。**

## 第十层：MDL 元数据锁 → 保护表结构

前面讲的锁保护的是**数据**。谁来保护**表结构**不被同时修改？

```
Session1: SELECT * FROM t;  -- 正在读数据
Session2: ALTER TABLE t ADD COLUMN c INT;  -- 同时在改表结构
  → 灾难！
```

**MDL（Metadata Lock）** 自动加，不需要手动：

| 操作 | MDL 类型 |
|------|------|
| SELECT/INSERT/UPDATE/DELETE | MDL 读锁 |
| ALTER TABLE / DROP TABLE | MDL 写锁 |

```
MDL 读锁之间兼容
MDL 写锁与读锁互斥

经典坑：
  事务长时间不提交 → 持有 MDL 读锁
  DDL 来了 → 等 MDL 写锁（排队）
  后续所有 SELECT → 被 DDL 阻塞（因为写锁  → 整个表不可用
```

> **第十层悟道：MDL 是表结构的"守护者"。事务不要长时间持有，否则一个 DDL 可能让整张表挂掉。**

## 第十一层：悲观锁 vs 乐观锁 → 两种哲学

这是锁的**思想流派**，不是 MySQL 的具体实现。

```
悲观锁：我先锁了再说，防止别人改
  → SELECT ... FOR UPDATE
  → 适合写冲突多的场景
  → 阻塞并发

乐观锁：我先读，改的时候再检查有没有别人改
  → version 字段 + CAS（Compare And Swap）
  → 适合读多写少的场景
  → 不阻塞，冲突时重试
```

```sql
-- 悲观锁
SELECT * FROM product WHERE id=1 FOR UPDATE;
UPDATE product SET stock=stock-1 WHERE id=1;

-- 乐观锁
SELECT stock, version FROM product WHERE id=1;  -- 得到 version=5
UPDATE product SET stock=stock-1, version=version+1 WHERE id=1 AND version=5;
-- 如果 affected_rows=0 → 说明 version 变了 → 别人改过 → 重试
```

> **第十一层悟道：悲观锁靠数据库锁住，乐观锁靠业务层 CAS 自旋。MySQL 的 FOR UPDATE 是悲观锁的实现。**

## 面试场景：如何一口气讲清楚 MySQL 锁？

**面试官：说说 MySQL 的锁机制。**

> 「MySQL 锁从三个维度看：粒度、模式、算法。
>
> **粒度**上分表锁和行锁。表锁简单但并发差，行锁精细但依赖索引——没索引会退化为全表锁。
>
> **模式**上分共享锁 S 和排他锁 X。S 锁共享读，X 锁独占写。注意普通 SELECT 不加 S 锁，走 MVCC 快照。
>
> **算法**上是 InnoDB 的核心：默认用 Next-Key Lock = Record Lock + Gap Lock。行锁锁已有记录，间隙锁锁空隙，一起防幻读。间隙锁是 RR 级别独有的，RC 不开。
>
> 协调机制上，意向锁 IS/IX 作为表级标记让表锁和行锁能共存。插入意向锁让同间隙不同位置的插入可以并发。
>
> 特殊锁有 AUTO-INC 锁保证自增不重复，MDL 锁保护表结构不被并发 DDL 破坏。
>
> 优化上防止锁升级（避免隐式类型转换导致索引失效），死锁防范（统一加锁顺序、缩短事务）。」

## 十种锁一句话总结

| 锁 | 一句话 |
|------|------|
| **表锁（读）** | 大家都能读，没人能写 |
| **表锁（写）** | 独占整张表，别人等 |
| **行锁** | 只锁命中行，依赖索引 |
| **S 锁** | 共享读，手动加：`LOCK IN SHARE MODE` |
| **X 锁** | 排他写，自动加：`FOR UPDATE` / `UPDATE` |
| **意向锁 IS/IX** | 表级路标，告诉表锁"表里有行被锁" |
| **Record Lock** | 锁具体一行记录 |
| **Gap Lock** | 锁记录间的空隙，防插入 |
| **Next-Key Lock** | Record + Gap，RR 默认，防幻读 |
| **插入意向锁** | 同间隙不同位置可并发插入 |
| **AUTO-INC 锁** | 保证自增主键并发不重复 |
| **MDL 锁** | 保护表结构，自动加，别长事务 |

## 个人总结

```
锁的方式：
读锁(S)： 加锁后别人也能读，但不能写。
写锁(X)： 加锁后别人不能读，也不能写。

共享锁 = 读锁。排他锁 = 写锁。同一套东西，两种叫法。

类别：
表锁： 针对整张表，并发差。分读锁和写锁。MyISAM 默认使用。
行锁： 针对具体行，并发好。InnoDB 默认使用，依赖索引。没索引退化为全表锁。

悲观锁： 默认"有人会跟我抢"，先 FOR UPDATE 锁上再操作，阻塞并发。
        适用写冲突多的场景。靠数据库 X 行锁实现。
乐观锁： 默认"不会有人跟我抢"，不加锁读，改时用 version 号判断冲突。
        冲突后业务代码重试。适用读多写少的场景。纯代码层面，数据库无锁。

间隙锁： RR 级别下，锁住记录之间的空隙，防止别人 INSERT，解决幻读。
        RC 级别不开间隙锁 → 可能幻读。
Next-Key Lock = 行锁 + 间隙锁，InnoDB RR 级别默认行锁算法。

意向锁： 表级标记，告诉表锁"表里有行被锁"。行锁加前先在表上插旗，
        避免表锁逐行检查。意向共享锁/意向排他锁之间不互斥，但与表级排他锁互斥。
        注意：不是和间隙锁配合，是和表锁配合！

插入意向锁：同间隙不同位置可并发插入。与 Gap Lock 互斥，插入意向锁之间兼容。

自增锁： 保证 AUTO_INCREMENT 列并发插入不重复。默认模式兼顾连续性和并发。

MDL锁： 保护表结构不被并发 DDL 破坏。自动加，长事务会堵死整张表。
```
