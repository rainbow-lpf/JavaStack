# 插入意向锁：从零到精通

> 三层递进，彻底吃透"同间隙不同位置可并发插入"这句话。

---

## 第一层：INSERT 本身也需要加锁

别以为 INSERT 不加锁。插入一行之前，InnoDB 要在这个间隙上打一个标记——**插入意向锁（Insert Intention Lock）**。

```
表中已有数据：[5]  [10]  [15]
间隙：[5]─┼─[10]─┼─[15]

Session: INSERT INTO t VALUES (7);
  ① 先在间隙 (5, 10) 上加"插入意向锁"
  ② 表示：我即将在这个间隙中插入 id=7
  ③ 锁加成功 → 实际执行插入
```

**插入意向锁就是一种特殊的 Gap Lock。它的作用是：告诉别人"我要在这个区间插数据"。**

---

## 第二层：有 Gap Lock 时 → 互斥，插入被阻塞

**插入意向锁和 Gap Lock 互斥。** 这是防幻读的核心。

```
表中数据：[5]  [10]  [15]

Session1:
  SELECT * FROM t WHERE id > 5 FOR UPDATE;
  → Next-Key Lock 锁住所有间隙 + 记录
  → 间隙 (5, 10) 上有了一个 Gap Lock

Session2:
  INSERT INTO t VALUES (7);
  → 想在 (5, 10) 上加插入意向锁
  → 但！间隙上已经有 Gap Lock 了
  → ❌ 互斥！阻塞等待！

Session3:
  INSERT INTO t VALUES (8);
  → 也想在 (5, 10) 上加插入意向锁
  → 间隙上 Gap Lock 还在
  → ❌ 也阻塞！

只有等 Session1 提交，Gap Lock 释放：
  Session2: 拿到插入意向锁 → 插入成功 ✅
  Session3: 拿到插入意向锁 → 插入成功 ✅
```

**这就是 RR 级别防幻读的本质：Gap Lock 堵着间隙，插入意向锁拿不到，谁也别想 INSERT。**

---

## 第三层：没有 Gap Lock 时 → 插入意向锁之间兼容，并发插入！

这才是"插入意向锁"设计的亮点。**没有 Gap Lock 的间隙，多个插入可以同时进行。**

```
表中数据：[5]  [10]  [15]
间隙 (5, 10)：干干净净，没有任何 Gap Lock

Session1: INSERT INTO t VALUES (7);
  → 加 (5, 10) 插入意向锁 ✅
  → 不阻塞别人，因为插入意向锁之间兼容

Session2: INSERT INTO t VALUES (8);
  → 也加 (5, 10) 插入意向锁 ✅
  → 和 Session1 的插入意向锁兼容！
  → 不阻塞！

Session3: INSERT INTO t VALUES (6);
  → 也加 (5, 10) 插入意向锁 ✅
  → 三个插入互不阻塞，同时进行！
```

**为什么能并发？**

```
同一个间隙，三个插入的位置不同：
  Session1 插 id=7
  Session2 插 id=8
  Session3 插 id=6

它们操作的是不同的行，只是碰巧在同一个间隙里。
插入意向锁之间不互斥 → 各自插各自的 → 高并发。
```

---

## 总览对比表

| 场景 | 插入是否阻塞 | 原因 |
|------|:---:|------|
| 间隙上有 **Gap Lock** | ❌ 阻塞 | Gap Lock 和插入意向锁**互斥** |
| 间隙上**只有插入意向锁**（多个） | ✅ 不阻塞 | 插入意向锁之间**兼容** |
| 间隙上**什么都没有** | ✅ 不阻塞 | 直接加插入意向锁 |

---

## 为什么这样设计？

```
设计目标：在保证数据一致性的前提下，最大化并发插入。

Gap Lock 存在时   → 有人在锁定这个区间（如 FOR UPDATE） → 插进去就幻读了 → 必须阻塞。

Gap Lock 不存在时 → 区间没人锁定，不同位置不会冲突 → 没必要互斥 → 并发插入。
```

---

## 一句话总结

```
Gap Lock 是"此路不通"的路障 → 插入意向锁被挡住。
没有 Gap Lock 时 → 插入意向锁之间和平共处 → 同一间隙多个插入互不阻塞。
```

**这就是"插入意向锁 = 间隙锁的并发优化版"的真正含义。**
