## ④ 火脸系统深挖要点(面试官追问时展开)

> 每点用 STAR(背景—问题—做法—结果)讲,挑面试官感兴趣的 2-3 个深入。

1. **三方支付渠道抽象解耦**
   - 问题:对接渠道多,原代码冗余、高耦合,新渠道接入困难、易出 Bug。
   - 做法:抽象三方支付模块、统一封装 SDK,用**模板方法 + 策略模式**把业务代码和支付渠道解耦。
   - 结果:新渠道接入成本大幅下降,迭代工作量和线上 Bug 明显减少。

2. **订单分库分表**
   - 问题:单库单表存订单,业务增长后出现性能瓶颈。
   - 做法:先按商户号分库分表 → 发现数据分布不均 → 改为按**时间维度**分库分表。
   - 结果:解决热点不均问题,提升了性能和水平扩展能力。
   - (可延伸:为什么商户号分不均、跨片查询怎么处理、分片键选型权衡。)

3. **RabbitMQ 高可用**
   - 问题:固定 IP 的镜像队列,节点宕机后无法恢复消费。
   - 做法:**Keepalived + HAProxy + 虚拟 IP**,做故障自动切换。
   - 结果:消息消费不再受单节点宕机影响,之后未再复现。

4. **Full GC 调优**
   - 问题:交易模块 Full GC 频繁且停顿长,导致交易超时;日志分析发现老年代占用过高。
   - 做法:调整 Full GC 触发时机(老年代约 70% 时触发),并配合内存与参数优化。
   - 结果:GC 停顿明显下降,系统响应和稳定性提升。
   - (可延伸:用的什么收集器、对象为什么晋升老年代、有没有从根因上减少对象。)

5. **分布式事务**
   - 问题:跨服务异常时数据不一致。
   - 做法:引入 **Seata,AT 模式**,保证跨服务数据一致性。
   - 结果:解决了分布式事务一致性问题。
   - (可延伸:为什么选 AT 而非 TCC / 最终一致 + 对账,各自取舍。)

6. **病毒勒索应急(可作为"抗压 / 责任心"类问题素材)**
   - 服务器遭勒索病毒、系统瘫痪,协调团队 24 小时紧急恢复;事后建立了完善的快照 / 备份机制。
   - (体现:应急响应、复盘改进意识。)

## ③ LOFTER 深挖要点(面试官追问时展开,主推)

> 这是最新、最能打的一段,电商 / 高并发岗重点讲。每点用「为什么这么设计 + 怎么落地 + 怎么保证正确性」展开。

### 1. 统一交易内核 + Hook 责任链(扩展性)

- **背景**:网易乐谷电商有普通商品订单和场馆周边订单两套交易,且不断要叠加各种营销玩法(赠品、兑换码、开心豆、库存扣减、商品计数等)。如果把这些逻辑硬塞进下单主流程,会越来越臃肿、改一个活动动全身。
- **做法**:抽象了一个 `MiniTradeHook` 扩展点接口,留了三个时机——`postTradeCreate`(事务内,下单落库前)、`afterTradeCreated`(事务后)、`afterReceiverChange`(收货信息变更)。每个营销玩法实现成一个独立 Hook(赠品 Hook、兑换码 Hook、开心豆 Hook、库存 Hook、商品计数 Hook 等),由 `MiniTradeHandlers` 用 `@Autowired List<MiniTradeHook>` 自动收集、按序回调。
- **效果**:核心下单链路和活动逻辑彻底解耦,加新活动只要加一个 Hook,不改主流程;事务内的 Hook(扣库存)和事务后的 Hook(发消息)时机分明。
- **可延伸**:为什么扣库存放事务内 Hook、发通知放事务后 Hook;Hook 抛异常怎么处理(我在 Handlers 里把异常透传出来让事务回滚);和策略模式 / 模板方法的区别。

### 2. 高并发下单模型——5 阶段防超卖 / 削峰(核心)

以场馆周边预约下单 `confirm` 为例,把整个下单切成有先后顺序的 5 个阶段:

- **入口分布式锁**:`Redisson` 按用户维度 `tryLock(3s)`,防同一用户并发 / 重复提交,拿不到锁直接返回"请勿重复提交"。
- **Phase 1 — Redis 库存预扣**:用 `RAtomicLong` 对时段库存 `addAndGet(1)`,这是最轻量的一道闸,超过时段上限立即拦截,把绝大多数无效请求挡在数据库之外。
- **Phase 2 — DB 校验**:通过预扣后才查库,做金额一致性校验(前端传的 sku 金额、总金额和后端重算结果必须一致,防篡改)和预约规则校验。
- **Phase 3 — 外部 I/O**:预留给银豹等第三方调用的位置,刻意和事务分开,避免外部 I/O 占用数据库连接、拉长事务。
- **Phase 4 — 统一事务**:交易、订单、订单商品、预约记录在一个事务里落库,保证原子性,事务内回调 Hook。
- **Phase 5 + finally 兜底**:事务成功就把"需要回滚预扣"标记置否;只要中途任何一步失败,`finally` 里自动把 Redis 预扣的库存 `addAndGet(-1)` 回滚,保证 Redis 计数和真实成单不会偏。
- **可延伸**:为什么先 Redis 后 DB(轻量拦截、保护 DB);预扣回滚和宕机场景怎么兜底(可加定时校准 / 过期);为什么金额要后端重算;锁粒度为什么按用户而不是按时段。

### 3. 自研滑动窗口限流(削峰)

- **做法**:基于 `Redisson` 的 `RScoredSortedSet`(ZSet)实现 `SlidingWindowRateLimiter`——以时间戳为 score,每次请求先 `removeRangeByScore` 清掉窗口外的旧记录,再 `count` 窗口内请求数,未超阈值才放行并写入。
- **为什么用滑动窗口**:相比固定窗口能避免临界点流量翻倍的问题,粒度更平滑。
- **可延伸**:和令牌桶 / 漏桶的取舍;ZSet 方案在高并发下的原子性问题(可用 Lua 脚本保证 remove+count+add 原子),这点可以主动讲,显示你想得够深。

### 4. 多营销活动的并发与防重

- 预约活动:时段粒度的库存预扣;兑换码活动:库存扣减 + 用户级锁防同一码 / 同一用户重复领取;赠品活动:支持自选和随机两种玩法,下单时校验赠品归属、达成条件。
- 共性:都靠"分布式锁 + Redis 计数 + DB 唯一约束 / 状态校验"三层来防超发、防重复。

### 5. 银豹(Pospal)第三方收银对接 + 订单补偿

- **背景**:线下提货走银豹收银系统,跨系统调用可能因网络 / 超时失败,导致订单卡在中间状态。
- **做法**:`PospalOrderCompensateTask` 定时补偿——分布式锁防多实例重复跑、"先查后建"保证幂等、按状态机分级推进(INIT→待提货→发货→完结)、失败重试有上限、超限告警、开关用 Apollo 动态控制。
- **可延伸**:为什么用补偿而不是强一致分布式事务(跨外部系统只能最终一致);幂等键怎么设计;告警怎么触发。

### 6. 自研 MockFilter 数据过滤框架

- 注解 + AOP 切面 + 本地缓存(定时异步刷新)+ 环境校验,对接口返回值(Map / 分页 / 集合 / 单对象)做策略化数据过滤,提升联调和灰度效率。体现造轮子和工程化能力。
