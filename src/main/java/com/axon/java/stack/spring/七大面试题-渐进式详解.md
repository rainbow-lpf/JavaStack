## 一、分布式事务一致性方案有哪些？

### 1.1 问题引入

单体时代：`@Transactional` 一个注解搞定——同一个 DB，同一个事务。

微服务时代：

```
下单：订单服务(库A) 扣库存 服务(库B) 扣余额 服务(库C)
      三个数据库，三个本地事务，互不感知
      库A成功、库B失败 → 数据不一致 💥
```

**这就是分布式事务要解决的问题：跨多个服务/数据库的操作，要么全成功，要么全失败。**

### 1.2 理论铺垫：CAP 与 BASE

```
CAP：分布式系统三者不可兼得
    C 一致性 / A 可用性 / P 分区容错（P 必选）
    → 只能在 C 和 A 之间取舍

BASE：Basic Available（基本可用）+ Soft state（软状态）+ Eventually consistent（最终一致）
    → 大厂互联网方案的共同哲学：放弃强一致，换高可用，靠补偿/重试/对账收敛
```

由此分布式事务分两大流派：**强一致（2PC/XA）** 和 **最终一致（TCC/Saga/事务消息/本地消息表）**。

### 1.3 2PC（两阶段提交 / XA）

```
阶段一（准备）：协调者问所有参与者"能提交吗？"
    → 参与者执行事务、锁住资源、写 redo/undo，但不提交，回复 YES/NO

阶段二（提交/回滚）：全部 YES → 下发提交；任一 NO → 下发回滚
```

| 问题 | 说明 |
|------|------|
| **同步阻塞** | 阶段一起所有参与者锁资源等待，吞吐骤降 |
| **协调者单点** | 协调者挂了，参与者资源一直锁着 |
| **二阶段不一致** | 部分收到 Commit 部分没收到 → 脑裂后数据不一致 |
| 性能差 | 一次事务 = 多轮网络往返 + 长时间持锁 |

3PC（三阶段）加了 CanCommit 预检 + 超时机制，仍解决不了网络分区下的不一致，**实际生产几乎不用**，了解即可。

### 1.4 TCC（Try-Confirm-Cancel）

业务层面的 2PC，每个参与方实现三个接口：

```
Try    ：预留资源。扣库存 → 冻结 1 件（不真扣）
Confirm：确认执行。冻结 → 真扣
Cancel ：取消释放。冻结额度退回
```

**三大经典坑（面试高频）：**

| 坑 | 场景 | 解法 |
|----|------|------|
| **空回滚** | Try 没执行（超时丢失），Cancel 先到了 | Cancel 检查事务记录：Try 不存在则记一条"已回滚"标记 |
| **悬挂** | Cancel 执行完，Try 才姗姗来迟 → 资源被冻结没人释放 | Try 执行前检查：事务已结束（回滚过）则拒绝 |
| **幂等** | Confirm/Cancel 重试多次 | 事务状态表 + 事务 ID 唯一约束，执行前查状态 |

**代价：业务侵入极大（一个操作写三个方法）+ 一张事务控制表。换来的：不依赖数据库 XA，性能好，隔离性由业务设计保证。**

### 1.5 Saga

长事务拆成一串**本地事务**，每个动作配一个**反向补偿**：

```
T1 订单   ──补偿 C1 删订单
T2 扣库存 ──补偿 C2 加回库存
T3 扣款   ✗ 失败 → 逆序执行 C2、C1 补偿
```

- **编排式**：状态机引擎统一调度（Seata Saga）
- **协同式**：每步完成发事件，下一步订阅触发（choreography）

**无隔离性**——中间状态对外可见，业务要设计成"可冲正"（如冻结而非直接扣）。适合流程长、参与方多（跨企业）的场景。

### 1.6 本地消息表

```
同一本地事务里：业务数据 + 消息记录 一起写入（原子）
后台任务扫描消息表 → 发 MQ → 标记已发
消费者幂等消费 → 最终一致
```

简单可靠，缺点是消息表和业务耦合、要自己写扫描任务。**RocketMQ 事务消息 = 把"本地消息表"下沉到 Broker，省掉自建。**

### 1.7 RocketMQ 事务消息

```
① 发半消息（消费者不可见）
② 执行本地事务
③ 成功 → Commit（消息可见）；失败 → Rollback（删除）
④ 长时间未决 → Broker 反查生产者"本地事务成没成？"
```

详见 `mq/RocketMQ-从零到面试.md` 第三章。

### 1.8 Seata AT 模式

对业务**零侵入**的"自动补偿"：

```
一阶段：拦截业务 SQL → 生成 undo log（前后镜像）→ 本地事务直接提交（快速释放锁）
        → 注册分支、申请全局锁
二阶段：全部成功 → 异步删除 undo log
        任一失败 → 按 undo log 反向 SQL 补偿
```

靠**全局锁**防脏写（防止一阶段提交后别的事务改了同一行）。性能远好于 XA，但全局锁是热点瓶颈。

### 1.9 选型决策 + 话术

```
追求强一致、内部短事务          → Seata AT / XA
高并发交易（下单扣库存扣款）    → 事务消息 / 本地消息表（最终一致）
需要资源预留、资金类强规则      → TCC
长流程、跨企业、步骤可补偿      → Saga
```

> **30 秒话术：** 我按一致性强弱选方案。强一致用 2PC/XA 或 Seata AT，代价是阻塞和锁；互联网高并发场景基本都走最终一致——先考虑事务消息，把本地事务和消息发送绑成一个原子动作，靠 Broker 反查兜底；需要资源预留就 TCC，但要处理空回滚、悬挂、幂等三件套；长流程跨企业用 Saga 正反服务。所有最终一致方案都要配**对账兜底**——没有对账的最终一致是不完整的。

## 二、RabbitMQ / RocketMQ / Kafka 的区别与选型

### 2.1 一张表看全

| 维度 | RabbitMQ | RocketMQ | Kafka |
|------|----------|----------|-------|
| 语言 | Erlang | Java | Scala/Java |
| 协议 | AMQP | 自研 Remoting | 自研（TCP） |
| 路由模型 | **Exchange 复杂路由**（direct/topic/fanout/headers） | Topic + Tag | Topic + Partition |
| 架构 | Broker 集群（镜像/仲裁队列） | **NameServer（无状态）+ Broker 主从** | ZK/KRaft + Broker 分区副本 ISR |
| 吞吐量 | 万级 | 十万级 | **百万级** |
| 延迟 | **微秒~毫秒**（最快） | 毫秒 | 毫秒（攒批） |
| 堆积能力 | 弱（百万级性能下降） | 强（亿级，顺序写磁盘） | **极强**（TB 级不动声色） |
| 事务消息 | ❌（有但性能差） | ✅ 两阶段+反查 | ❌（无事务消息语义） |
| 延迟消息 | 插件 | ✅ 18 级别 / 5.x 任意 | ❌ |
| 消息回溯 | ❌ 消费即删 | ✅ 按时间/offset | ✅ 按 offset/时间 |
| 功能丰富度 | 中（管理界面最好） | **最全**（轨迹/重试/死信） | 少（专注流） |

### 2.2 设计哲学差异（进阶理解）

```
RabbitMQ：消息代理（Broker）思路——复杂路由，推模式，消息消费即删
Kafka  ：分布式日志（Log）思路——消息是"流"，Append-Only 顺序写，
         消费者靠 offset 自己拉，读完不删，天然支持回溯和重复消费
RocketMQ：取两者中间——学 Kafka 的顺序写存储，但补齐了业务功能
         （事务/延迟/重试/死信/轨迹），面向交易业务设计
```

- Kafka 快在**攒批发送 + 顺序写磁盘 + 零拷贝（sendfile）**，但攒批带来毫秒级延迟
- RabbitMQ 推模式 + Erlang 天生低延迟，但 Erlang 队列堆积大了会**内存告警、性能滑坡**
- RocketMQ 的 CommitLog 所有 Topic 混写一个文件（顺序写），ConsumeQueue 做索引

### 2.3 场景选型

| 场景 | 选型 | 原因 |
|------|------|------|
| 日志采集、埋点、大数据流 | **Kafka** | 百万吞吐、生态（Flink/Spark）、可回溯 |
| 电商交易、订单、支付 | **RocketMQ** | 事务消息、顺序消息、堆积强、业务功能全 |
| 中小系统、复杂路由、低延迟通知 | **RabbitMQ** | AMQP 灵活路由、管理方便、微秒延迟 |
| IoT 物联网海量上报 | Kafka | 吞吐 + 削峰 |

> **30 秒话术：** 三个定位不同：Kafka 是分布式日志，为大数据流而生，百万吞吐靠攒批+顺序写+零拷贝；RabbitMQ 是消息代理，AMQP 路由最灵活、延迟最低，但堆积弱；RocketMQ 是为交易业务设计的——Kafka 的存储骨架 + 补齐事务消息、延迟消息、消息轨迹这些业务刚需。我司交易链路用 RocketMQ（下单发事务消息保证本地事务与消息原子），日志链路用 Kafka，任务分发用 RabbitMQ。

## 三、RocketMQ 消息类型 + 顺序消息 + 事务消息回查

### 3.1 消息类型盘点

| 类型 | 说明 |
|------|------|
| 普通消息 | 默认，无顺序、无事务保证 |
| **顺序消息** | 全局顺序（一 Topic 一队列）/ 分区顺序（按 shardingKey 一队列） |
| **延迟消息** | 4.x：18 个固定级别（1s~2h）；5.x：任意时间定时 |
| **事务消息** | 半消息 + 本地事务 + 反查（见下） |
| 批量消息 | 一次发多条（同一 Topic，总大小 ≤ 4MB） |
| 消息轨迹 | 5.x 消息查询/轨迹追踪 |

### 3.2 顺序消息实现原理

要保证顺序，必须**三个环节都顺序**：

```
① 生产端：同一 shardingKey 的消息进同一个 Queue
   producer.send(msg, (mqs, msg, arg) -> {
       int index = arg.hashCode() % mqs.size();   // MessageQueueSelector
       return mqs.get(index);                      // 订单号 → 固定队列
   });

② 存储端：单个 Queue 天然 FIFO
   CommitLog 顺序写 + ConsumeQueue 按 queue 组织，offset 单调递增

③ 消费端：MessageListenerOrderly——单线程消费一个 Queue
   Broker 给队列上分布式锁，消费端对 ProcessQueue 加锁
   → 一个 queue 同时只有一个消费者线程在处理
```

**两个坑：**

1. 生产端**同步发送 + 重试**时失败可能换队列重发 → 乱序，顺序消息要关重试或业务容忍
2. 消费失败会**阻塞整个队列**（后面消息不能跳过）→ 必须配最大重试次数 + 告警人工介入，否则一个毒消息堵死一条队列
3. 顺序消息吞吐低：一个 key 一个队列一个线程，热点 key 是瓶颈

### 3.3 事务消息：回查达到最大次数后，半消息怎么处理？

先回顾机制：

```
半消息存储结构（两个系统 Topic）：
  RMQ_SYS_TRANS_HALF_TOPIC     半消息暂存（消费者不可见）
  RMQ_SYS_TRANS_OP_HALF_TOPIC  已处理（commit/rollback）的标记
回查：Broker 定时扫 HALF topic，不在 OP 里 → 反查 Producer
```

**关键答案：达到最大回查次数（`transactionCheckMax`，默认 15 次）后，Broker 会丢弃该半消息**——不再投递给消费者，仅打印日志。也就是说：**消息没了，本地事务和消息投递的绑定关系断掉，必须靠业务侧兜底。**

排查步骤：

```
① 定位半消息：控制台按 Topic/Key 查消息，看是否卡在 RMQ_SYS_TRANS_HALF_TOPIC
② 查 Broker 日志：搜 "check transaction message" / 达到最大回查的 discard 日志
③ 反查生产者为什么一直不返回状态：
   a. Producer 进程重启/宕机，回查时无人应答
   b. checkLocalTransaction 实现里查不到本地事务状态记录
      → 根因往往是：事务执行结果没有【持久化】（半消息状态表缺失）
      → 回查时业务自己也不知道"成没成"
   c. 回查线程被阻塞、网络不通
④ 业务侧兜底：本地事务状态表 + 定时对账
   → 对账发现"本地事务成功但消息丢了" → 补发消息 / 直接调下游补偿
```

**根因提醒：事务回查的前提是"能回答本地事务成没成"——所以事务执行结果必须落库（状态表或直接查业务表）。没有持久化状态的事务消息，回查必然超限。**

### 3.4 话术

> 顺序消息三环节：生产端 MessageQueueSelector 按 shardingKey 进同队列，存储端单队列 FIFO，消费端 Orderly 监听器单线程消费加队列锁。事务消息回查默认 15 次，超限后 Broker 直接丢弃半消息——所以业务必须落本地事务状态表，让回查能答上"成没成"，再配对账兜底。排查时从控制台查半消息卡在哪个系统 Topic，看 Broker 回查日志，再顺藤摸瓜查 Producer 的应答链路。

## 四、Redis 库存与 DB 库存一致性（电商）

### 4.1 先定调：一致性定位

```
追求强一致（分布式锁同步刷）→ 高并发下性能崩溃，本末倒置
正确姿势：Redis 是"挡板/配额"，DB 是"真账本"
        → 只保证【不超卖】（强约束），允许【短暂不一致】（异步收敛）
```

### 4.2 你答的"分布式锁"——能用，但问题很多

| 问题 | 说明 |
|------|------|
| **性能瓶颈** | 所有请求串行化，秒杀场景 QPS 直接掉一个量级——锁成了新瓶颈 |
| 锁过期业务没跑完 | 任务没执行完锁先过期 → 并发进来 → 还得加续期（看门狗） |
| Redis 主从切换丢锁 | 主挂锁没同步到从 → 两个客户端同时持锁（RedLock 也有争议） |
| 死锁风险 | 业务异常没走到 unlock → 依赖过期时间兜底 |
| 治标不治本 | 锁只解决"同时改"，不解决"两边数据一致"——锁内还是要面对 Redis 扣了 DB 失败怎么办 |

### 4.3 推荐方案：分层拆解

**方案 A：Redis 原子扣减 + MQ 异步落库（主流，最终一致）**

```
① Lua 脚本原子扣减 Redis（check-and-decrement 一体，防超卖的关键）
   if stock >= 1 then stock -= 1; return 1; else return 0
② 扣成功 → 发 MQ → 消费者更新 DB（创建订单 + DB 扣减）
③ DB 成功 → 完成；DB 失败 → 补偿：回补 Redis 库存 + 取消订单
不一致窗口 = MQ 消费延迟（毫秒~秒级），DB 永远是真账本
```

**方案 B：DB 条件更新兜底防超卖（万无一失的最后防线）**

```sql
UPDATE stock SET num = num - 1 WHERE sku_id = ? AND num > 0
-- 影响行数 = 0 → 卖完了 → 走回滚补偿
```

无论 Redis 怎么玩，DB 层这条 SQL 保证**永不超卖**。

**方案 C：预扣 + 确认 + 超时回补（订单生命周期式）**

```
下单 → Redis 预扣（冻结）→ 15 分钟未支付 → 延迟消息回补库存
支付成功 → 预扣转实扣 → 异步同步 DB
```

**方案 D：库存分桶（热点优化）**

```
一个 key 扣减打满 Redis 单线程 → 拆成 stock_0~stock_9 十个桶轮询扣
→ 并发提升 10 倍；桶间不平衡靠"扣不动就挪桶"
```

**方案 E：对账兜底（最终一致的收口）**

```
定时任务比对 Redis 库存 vs DB 库存
差异 → 以 DB 为准修正 Redis + 告警
没有对账的一致性方案都是裸奔
```

### 4.4 话术

> 我不追求 Redis 和 DB 的强一致——那得靠分布式锁串行化，性能先崩。我的方案：Redis Lua 原子扣减做挡板防超卖，扣成功发 MQ 异步落库，DB 用条件更新 `WHERE num > 0` 做最后防线，DB 失败走补偿回补 Redis，再配定时对账以 DB 为准修正缓存。热点 SKU 上库存分桶提升扣减并发。本质是：**不超卖是强约束，库存数短暂不一致靠异步收敛——最终一致 + 对账兜底。**

## 五、系统重构：用户无感 + 数据迁移 + 双写

### 5.1 全景：无感迁移四部曲

```
① 全量迁移：旧库 → 新库（DTS / Canal / 数据导入，历史数据）
② 增量同步：binlog 持续把旧库的增量写进新库（追平）
③ 双写切换：新应用上线，写新库（此时读还是旧的）→ 新旧数据一致
④ 灰度切读：按用户尾号/白名单/百分比灰度读新库
    → 新旧双读比对（shadow read）：不一致打日志 → 修复
    → 逐步放量 100% → 观察稳定 → 停写旧库，迁移完成
```

### 5.2 双写两条路：改代码 vs binlog，哪个好？

| | 改代码双写（业务代码里写新旧两库） | binlog 同步（Canal 订阅旧库→写新库） |
|---|---|---|
| 侵入性 | 高，业务代码到处改 | **零侵入**，不动业务代码 |
| 一致性 | 同事务内可保证强一致（同库时） | 异步，最终一致（有延迟窗口） |
| 性能 | 写放大，RT 增加 | 影响小 |
| 变更灵活性 | 业务语义清楚（知道该写什么） | 逐行搬运，新库结构变了要维护解析逻辑 |
| 下线成本 | 还要再改一次代码摘掉旧库 | 改配置停同步即可 |
| 适用 | **切换窗口期的强一致保障** | **全量+增量打底、长期同步** |

**结论：不是二选一，是组合拳——**

```
binlog 负责"数据搬运"：全量初始化 + 增量追平 + 校验
代码双写负责"切换窗口"：灰度读新库期间，写必须同时落新旧两库保证可随时回滚
                        （binlog 延迟窗口内，双写保证新旧库都能服务）
最后：停代码双写 → 停 binlog → 旧库下线
```

### 5.3 双写引发的问题（面试官追问点）

| 问题 | 说明 | 解法 |
|------|------|------|
| **双写不一致** | 两次写不是原子的，一成一败 | 以旧库为准修新库 + 补偿任务 + 差异校验 |
| **性能翻倍** | 每次请求两倍 DB 压力 | 新库写异步化（MQ）或压测扩容 |
| **自增 ID / 唯一键冲突** | 新旧库各自自增 | 新库直接沿用旧库主键，不自增 |
| **事务边界** | 跨库双写无法用一个事务 | 同步双写尽量包在一起 + 失败补偿 |
| **binlog 延迟窗口** | 读新库时 binlog 还没追到 | 灰度期间双读比对、只读场景延迟容忍 |
| **回滚困难** | 切了流量才发现新库有问题 | 双写期间旧库一直是"最新真相"，可随时切回 |

### 5.4 话术

> 无感迁移四步：全量 + 增量（binlog）打底 → 双写保证切换期一致 → 灰度读新库 + 双读比对 → 逐步放量下线旧库。双写方案我选组合：binlog 做数据搬运零侵入，代码双写保切换窗口强一致可回滚。双写最大的坑是非原子导致的不一致——靠"旧库为准 + 差异校验 + 补偿"收敛，且灰度期间旧库永远保留最新数据作为回滚底气。

## 六、防止同一笔订单被重复支付（电商/支付）

### 6.1 重复支付从哪来

```
① 用户手抖连点两次"支付"
② 多端同时发起（App + H5 + 网页）
③ 超时重试（前端重试 / 网关重试 / 用户刷新）
④ 支付渠道回调重复通知（微信/支付宝会多次回调）
```

### 6.2 方案分层（从入口到兜底）

**第 1 层：前端防重**

按钮点击后置灰 + loading，防手抖。**只能挡君子，后端必须幂等。**

**第 2 层：应用层幂等——唯一约束（最强兜底）**

```sql
支付流水表：UNIQUE KEY uk_request_id (request_id)
          或 UNIQUE KEY uk_order_channel (order_id, channel)
-- 重复请求 insert 报 DuplicateKeyException → 直接返回原支付单/上次结果
```

**"先查后插"不可靠（并发穿透），唯一索引才是硬保障。**

**第 3 层：状态机 + CAS 更新**

```sql
UPDATE pay_order SET status = 'PAYING'
WHERE order_id = ? AND status = 'INIT'
-- 影响行数 = 0 → 已经有人在支付/已支付 → 返回当前状态，不创建新支付单
```

**第 4 层：分布式锁辅助**

按 `order_id` 加锁串行化进入支付逻辑——**辅助手段，不能单靠它**（锁服务不可用时仍需唯一索引兜底）。

**第 5 层：支付渠道侧幂等**

```
同一订单号向微信/支付宝多次下单：
  → 渠道侧 prepay_id 可复用，渠道保证同一商户订单号只成功扣款一次
  → 自己生成的 out_trade_no 必须对同一订单稳定（不能每次随机生成！）
```

**第 6 层：回调幂等（通知会来很多次）**

```
回调流水表：UNIQUE KEY uk_trade_no (channel_trade_no)  → 通知去重
+ 状态机：只有 PAYING → PAID 才处理后续（发货/加积分）
重复回调：查到已 PAID → 直接返回 success，业务不重复执行
```

**第 7 层：资金对账兜底（最终防线）**

```
每日对账：渠道对账单 vs 平台支付流水
发现"一笔订单两笔成功流水"（理论不应发生，但渠道异常可能）
→ 自动/人工发起原路退款 + 告警
```

### 6.3 完整链路图

```
点击支付
  → 前端置灰
  → 后端锁 order_id
  → 状态机 CAS：INIT → PAYING（失败=已在支付，返回）
  → 创建支付流水（唯一索引兜底）
  → 调渠道（out_trade_no 固定，渠道幂等）
  → 回调：流水唯一索引去重 + 状态机 PAYING→PAID
  → 业务执行幂等（发货/积分唯一约束）
  → 日终对账兜底
```

### 6.4 话术

> 防重复支付是纵深防御：前端防抖挡手抖，后端靠**状态机 CAS + 唯一索引**做幂等——这是硬保障，锁只是辅助；渠道侧靠固定的商户订单号让微信/支付宝自己幂等；回调用流水表唯一约束去重 + 状态机推进，重复通知直接回 success；最后每日对账兜底，真发生多付就自动原路退款。核心思想：**每一层都假设上一层会失效，数据库唯一索引和状态机是最后的墙。**

## 七、活动预热 + Spring 扩展点

### 7.1 预热是什么

大促/活动开始前，**提前把"活动开始瞬间会被疯狂访问的东西"准备好**：

| 预热对象 | 做什么 |
|---------|--------|
| **缓存预热** | 活动配置、商品详情、库存数提前写进 Redis / 本地缓存 |
| **DB 预热** | 预跑热点 SQL，让索引页/数据页进 Buffer Pool |
| **连接预热** | 提前建立 DB 连接池、Redis 连接、HTTP 连接（首次建连最慢） |
| **JVM 预热** | 预跑核心接口让 JIT 编译热点代码、触发类加载 |
| **容量预热** | 提前扩容实例、注册到网关、MQ 预建队列 |

**不预热的下场：活动开始瞬间缓存全空 → 请求全部打到 DB（缓存击穿/雪崩）→ DB 打挂 → 全链路雪崩。**

### 7.2 Spring 容器的扩展接口（本题考点）

预热代码要"在容器启动完成后自动执行"，可用扩展点按时机排序：

```
Bean 级（太早，不适合预热）：
  @PostConstruct / InitializingBean.afterPropertiesSet
      → 单个 Bean 初始化完就执行，此时其他 Bean/中间件可能还没就绪 ❌

容器级（合适）：
  ① SmartInitializingSingleton
       → 所有单例 Bean 初始化完成后回调 ✅

  ② SmartLifecycle.start()
       → 容器刷新完成阶段回调，可控制 phase 顺序，还能 stop ✅

  ③ ApplicationListener<ApplicationReadyEvent> / @EventListener
       → Spring Boot 完全启动就绪（含 Web 容器）后发布，最常用 ✅✅

  ④ CommandLineRunner / ApplicationRunner
       → 启动完成后按顺序执行（Spring Boot），比 ReadyEvent 早一点 ✅
```

### 7.3 预热实现示例

```java
@Component
public class ActivityWarmUpRunner implements ApplicationRunner {

    @Resource private ActivityService activityService;
    @Resource private StringRedisTemplate redis;

    @Override
    public void run(ApplicationArguments args) {
        // 异步预热，不阻塞启动
        CompletableFuture.runAsync(this::warmUp);
    }

    private void warmUp() {
        List<Activity> activities = activityService.listUpcoming();
        for (Activity a : activities) {
            // ① 配置预热进 Redis，TTL 设到活动结束
            redis.opsForValue().set("activity:" + a.getId(),
                    JSON.toJSONString(a),
                    Duration.between(now, a.getEndTime()));
            // ② 库存预热
            redis.opsForValue().set("stock:" + a.getSkuId(),
                    String.valueOf(a.getTotalStock()));
            // ③ 本地缓存 + 预跑一次热点查询（DB 预热 + JIT）
            localCache.put(a.getId(), a);
        }
        log.info("activity warm up done, count={}", activities.size());
        // 失败要告警——预热失败 = 活动裸奔
    }
}
```

**三个注意点：**
1. **异步执行**：预热别阻塞应用启动
2. **失败告警**：预热失败必须重试/告警，否则活动开始就是缓存雪崩
3. **TTL 管理**：缓存过期时间 ≥ 活动结束时间，别让缓存中途过期

### 7.4 话术

> 活动预热就是提前把活动开始瞬间的热点数据、连接、JIT、容量准备好，避免冷启动时缓存击穿打挂 DB。Spring 扩展点上，Bean 级的 @PostConstruct 太早不敢用，容器级我用 ApplicationRunner 或监听 ApplicationReadyEvent——应用完全就绪后异步执行：活动配置和库存写 Redis（TTL 到活动结束）、本地缓存加载、预跑热点 SQL 做 DB 和 JIT 预热，失败重试告警。再配合提前扩容注册网关，活动开始时全链路都是热的。
