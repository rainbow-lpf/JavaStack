# MySQL 多字段分库分表

> 一个表多个查询维度，怎么分？——基因法、异构索引、ES、广播四招

---

## 一、核心矛盾（先把题眼点破）

**一张物理表只有一个路由算法、一个分片键。**

订单表既有 `order_id` 查、又有 `user_id` 查、还有 `merchant_id` 查——分片键选谁，谁就精确路由，**其他维度全是全分片广播**。

| 查询场景 | 分片键=user_id | 分片键=order_id |
|---------|:---:|:---:|
| `WHERE user_id = ?` | ✅ 命中单分片 | ❌ 广播 |
| `WHERE order_id = ?` | ❌ 广播 | ✅ 命中单分片 |
| `WHERE merchant_id = ?` | ❌ 广播 | ❌ 广播 |

所以"多字段怎么分"的答案不是"选一个字段"，而是：**主分片键选最高频维度，其余维度用下面四招补**。

---

## 二、方案一：基因法（最经典，面试必讲）

**把 A 键的"基因"嵌入 B 键里**，让 B 键自带 A 键的路由信息。

### 原理

```
雪花算法改造：
  41位时间戳 | 10位机器ID | 12位序列
                    ↓ 改成
  41位时间戳 | user_id 低8位基因 | 12位序列     ← 生成 order_id 时嵌入

分表 256 张（2^8）：
  按 order_id 查：order_id % 256 → 路由（基因位就是取模位）✅
  按 user_id  查：user_id % 256 → 同一片 ✅（order_id 里嵌的就是 user_id % 256）
```

### 伪代码

```
生成订单：order_id = snowflake() 但序列段填 user_id & 0xFF
查询订单：WHERE user_id=9527 → 9527 % 256 = 184 → 去第 184 张表 ✅
```

### 优缺点

| 优点 | 缺点 |
|------|------|
| 一份数据、零冗余、强一致 | 基因位数决定分片数上限（8 位 → 最多 256 片） |
| 查询无感知，SQL 不用改 | id 生成器要自己改造 |
| 无二次查询开销 | 只能救一个维度（两个基因就挤爆位数） |

## 三、方案二：异构索引表（空间换时间）

**同一份数据按不同分片键各存一份**：

```
订单主表 t_order          → 按 user_id 分 8 片（买家维度，最高频）
订单异构表 t_order_seller → 按 merchant_id 分片（商家维度）
```

### 数据同步两种方式

```
方式 1：双写 —— 写主表 + 异构表（本地事务/事务消息保证一致）
方式 2：binlog —— 写主表 + Canal 监听 binlog 异步写异构表（最终一致，延迟毫秒级）
```

### 优缺点

| 优点 | 缺点 |
|------|------|
| 各维度查询都精确路由 | 存储翻倍 |
| 异构表可以只存索引字段 + 主键，很薄 | 一致性从强变最终 |
| 维度数量不限，加维度加表 | 写放大 |

**实战要点：异构表通常只做"索引"——只存 `merchant_id + order_id`，查到 order_id 列表再回主表取详情。**

---

## 四、方案三：外置索引（ES / 映射表）

```
非分片键查询 → 先查 ES/映射表拿分片键 → 再精确路由回库

例：运营后台按 status='PAID' 查订单
  → ES（订单宽表，binlog 同步）查出 order_id + user_id 列表
  → 拿 user_id % 256 路由回 MySQL 批量取详情
```

### 优缺点

| 优点 | 缺点 |
|------|------|
| 任意维度任意组合 | 引入 ES 运维成本 |
| 顺带解决复杂搜索、深度分页 | 一致性靠同步链路 |

**适合低频运营/后台查询**——核心交易链路不依赖它，ES 挂了只影响后台，不影响下单。

---

## 五、方案四：广播查询（兜底，尽量别用）

不带分片键 → ShardingSphere 广播到所有片 → 流式归并。

```
适用：分片少、数据少、低频查询
问题：N 片 = N 倍数据库压力 + 归并内存压力，深度分页雪上加霜
```

---

## 六、选型决策

```
维度优先级排序（按查询 QPS）：
  最高频维度 → 主分片键
  第二高频维度 → 基因法（能改造 id 就用，成本最低）
  第三维度 → 异构索引表（薄索引 + 回表）
  低频运营/搜索/聚合 → ES
  都不想建 → 广播兜底（确认分片数和数据量可接受）
```

**核心思想：按查询频率分配成本——越高频的维度越要精确路由，越低频的越可以容忍二次查询或异步索引。**

---

## 七、面试总结话术（30 秒）

> 一张表只有一个路由算法，多字段查询的本质是"一主多辅"：主分片键选最高频维度；第二维度用基因法——把用户 id 的低位嵌入订单 id 生成逻辑，两键取模同片，零冗余强一致；再多的维度用异构索引表，binlog 异步同步一份薄索引（只存维度 + 主键）再回主表；运营后台的复杂查询丢给 ES。广播查询是最后兜底，只在分片数少时可用。
