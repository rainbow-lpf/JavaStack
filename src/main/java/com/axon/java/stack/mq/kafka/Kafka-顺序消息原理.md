# Kafka 顺序消息原理

> 分区内有序，跨分区无序——和 RocketMQ 分区顺序同思路，但实现细节不同

---

## 一、核心结论

```
Kafka 只在【分区内】保证有序，【跨分区】无顺序
→ 同一 key 的消息 hash 到同一分区 → key 内有序

和 RocketMQ 分区顺序同思路：
  Kafka    key → partition
  RocketMQ key → MessageQueue
```

---

## 二、三环节锁顺序

### 环节 1：生产端——key 决定分区

```java
// 同一 key 永远进同一分区（默认分区器：key.hashCode % 分区数）
producer.send(new ProducerRecord<>("topic", "order123", body));
// key="order123" → 同一分区 → 分区内按追加顺序有序
```

```
order123 → 永远 partition-2
order456 → 永远 partition-0
→ 单分区内有序，跨分区无顺序
```

**注意**：Kafka 是攒批发送，同一分区内消息按追加进日志的顺序有序——攒批不会打乱分区内顺序。

### 环节 2：存储端——分区日志 append-only

```
partition 是一个 append-only 的日志：
  [msg1] [msg2] [msg3] ... 只能往后追加
  每条消息有单调递增的 offset
→ 存储层天然有序，offset 就是顺序依据
```

### 环节 3：消费端——单分区单线程消费

```
同一分区同一时刻只被【组内一个消费者】的【一个线程】处理
→ 天然串行消费，有序
```

## 三、会破坏顺序的三件事（面试必问）

| 破坏点 | 说明 | 对策 |
|--------|------|------|
| **消费失败重试** | 失败后提交 offset 再拉 → 后面消息先处理 → 乱序 | 顺序场景禁止自动重试提交，失败阻塞等待人工/重试同一条 |
| **Rebalance** | 消费者组内成员变动 → 分区重新分配 → 可能重复消费 | 幂等兜底，顺序靠单分区单线程的重新建立 |
| **消费者内多线程** | 一条消息开一个线程异步处理 → 乱序 | 顺序场景单线程处理 |

**核心：Kafka 保证"分区内有序"，但"恰好一次消费 + 有序"要业务自己配合。**

---

## 四、和 RocketMQ 顺序消息的差异

| | RocketMQ | Kafka |
|---|----------|-------|
| 队列模型 | MessageQueue | Partition |
| key 路由 | MessageQueueSelector | 分区器 key.hashCode |
| 有序范围 | 队列内 | 分区内 |
| 消费失败 | 原地 SUSPEND 重试（Orderly） | 无原生顺序重试，需自己处理 |
| 破坏点 | 同步发送重试换队列 | Rebalance 重复消费 |

---

## 五、面试话术（30 秒）

> Kafka 顺序消息只在分区内保证有序，跨分区无序。三环节：生产端同一 key hash 到同一分区；存储端分区是 append-only 日志，offset 单调递增天然有序；消费端单分区单消费者单线程串行处理。会破坏顺序的三件事：消费失败自动提交 offset 重试、消费者组 Rebalance 导致重复、消费者内多线程处理——顺序场景都要规避。和 RocketMQ 思路一样都是 key 路由到单队列/单分区，差异在于 Kafka 没有原生的顺序重试机制，失败要自己阻塞处理。

---

## 附：何时用 Kafka 做顺序

```
Kafka 顺序适合：日志、埋点、流处理（天然按分区有序即可）
强业务顺序（订单状态机）：RocketMQ 分区顺序更顺手（有 Orderly 重试语义）
```
