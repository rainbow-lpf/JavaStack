> **总结日期：** 2026-07-07
> **核心主题：** CAP 理论 + Dubbo 注册中心选型

---

## 一、CAP 理论

| 字母 | 全称 | 含义 | 通俗说法 |
|---|---|---|---|
| **C** | Consistency | 一致性 | 所有节点同一时刻看到的数据完全相同 |
| **A** | Availability | 可用性 | 每个请求都能拿到一个响应（不报错，不超时） |
| **P** | Partition Tolerance | 分区容错性 | 节点之间网络断了，系统仍能对外服务 |

---

## 二、核心结论

> **P 必须选。** 分布式系统中网络分区无法避免，只能在 C 和 A 之间二选一。

```
          P（必须）
         /      \
       C         A
      （一致）  （可用）
     只能二选一
```

- **CP 系统：** 网络分区时选一致性 → 拒绝写入 → 牺牲可用性
- **AP 系统：** 网络分区时选可用性 → 允许写入 → 数据可能暂时不一致
- **CA 系统：** 不存在于分布式系统中（除非单机，没有网络分区）

---

## 三、常见注册中心选型

| 注册中心 | CAP 选型 | 行为 |
|---|---|---|
| **Zookeeper** | **CP** | 主节点挂了 → 选举期间不可写 → 牺牲可用性 |
| **Eureka** | **AP** | 节点间网络断 → 各自保留注册信息 → 数据可能不一致 |
| **Nacos** | **AP / CP 可切换** | 默认 AP；也可切换到 CP 模式（Raft 协议） |
| **Consul** | **CP** | Raft 协议，选举期间不可写 |

---

## 四、为什么 Dubbo 注册中心倾向 AP

Dubbo 注册中心的职责是**服务发现**，不是数据存储：

```
注册中心不可用（CP 脑裂不可写）
  → Consumer 拿不到最新 Provider 列表
  → 调用可能失败
  ❌ 不可接受

注册中心数据暂时不一致（AP 各节点数据有差异）
  → Consumer 拿到旧地址，调用失败
  → Dubbo 有 failover 容错，自动重试其他节点
  ✅ 可接受
```

**Dubbo 用了三层容错让 AP 的不一致性变得可接受：**

| 层级 | 机制 | 作用 |
|---|---|---|
| 注册中心 | AP 选型 | 高可用，不阻塞服务发现 |
| 本地文件缓存 | 磁盘兜底 | 注册中心挂了还能拿到旧列表 |
| Cluster 容错 | failover 重试 | 调到旧节点失败自动换下一个 |

**结论：** AP 牺牲的一致性，通过 failover 容错补回来了，所以 Dubbo 注册中心优先选 AP。

---

## 五、Nacos AP vs CP

| 模式 | 一致性问题 | 可用性问题 |
|---|---|---|
| AP（默认） | 临时节点，网络分区时不同节点数据可能不一致 | 高，始终可读写 |
| CP（Raft） | 强一致，所有节点数据统一 | 网络分区时少数派节点拒绝写入 |

**使用场景：**
- 服务注册发现：用 AP（临时节点，高可用优先）
- 配置中心：用 CP（持久化节点，数据一致性优先）

---

## 六、面试口述

> "CAP 理论就是说，分布式系统 P 必须保证，C 和 A 只能二选一。ZK 选 CP，选举期间不可写；Eureka 和 Nacos 默认选 AP，允许数据暂时不一致但始终可用。
>
> Dubbo 注册中心用 AP 就行，因为服务发现对一致性要求不高。就算 Consumer 拿到旧地址调用失败，Dubbo 还有 failover 容错自动重试别的节点，再加上本地文件缓存兜底，整体可靠性不受影响。
>
> 所以 Dubbo + Nacos 是典型的 AP 架构：注册中心高可用优先，一致性靠 failover + 本地缓存补位。"
