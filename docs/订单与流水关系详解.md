# 订单与流水关系详解

## 1. 核心结论

在电商和支付业务中，可以先记住一句话：

**订单是“买卖业务”的记录，流水是“资金动作”的记录。**

订单关注的是：

- 谁买了什么
- 买了多少
- 应付多少钱
- 订单当前处于什么业务状态
- 是否发货、收货、取消、退款

流水关注的是：

- 钱是否发生了变动
- 发生了哪一种资金动作
- 金额是多少
- 通过什么渠道完成
- 第三方支付平台返回了什么交易号
- 这次资金动作是成功、失败还是处理中

因此，订单表和流水表不是重复关系，而是从两个不同视角记录同一笔交易过程。

常见关系是：

```text
一个订单 : 多条流水 = 1 : N
```

一个订单可能对应多次支付尝试、多次退款、手续费、分账、结算等多条流水。

---

## 2. 什么是订单

订单是业务交易的主体记录。

在电商系统中，用户点击“提交订单”之后，系统通常会生成一条订单记录。订单记录描述的是这笔买卖本身。

例如：

```text
订单号：O1001
用户：U001
商品：手机壳
商品金额：100 元
优惠金额：10 元
运费：0 元
应付金额：90 元
订单状态：待支付
```

订单表通常记录的是业务层面的信息。

示例字段：

| 字段 | 含义 |
| --- | --- |
| order_id | 业务订单号 |
| user_id | 下单用户 |
| order_amount | 订单原始金额 |
| discount_amount | 优惠金额 |
| freight_amount | 运费 |
| pay_amount | 应付金额 |
| paid_amount | 已支付金额 |
| refunded_amount | 已退款金额 |
| status | 订单状态 |
| created_at | 下单时间 |
| paid_at | 支付成功时间 |
| canceled_at | 取消时间 |
| completed_at | 完成时间 |

订单状态通常包括：

```text
待支付
已支付
已发货
已完成
已取消
部分退款
已退款
```

订单表的核心作用是承载业务流程。

---

## 3. 什么是流水

流水是资金动作的明细记录。

只要系统里发生了一次和资金相关的动作，就可以记录一条流水。例如：

- 用户支付
- 支付失败
- 用户退款
- 平台扣手续费
- 商户入账
- 钱包余额扣减
- 钱包余额增加
- 商户提现
- 平台结算

支付流水表示“某一次支付渠道请求及其结果”。

例如：

```text
流水号：F9001
关联订单：O1001
流水类型：支付
金额：90 元
支付渠道：支付宝
状态：成功
支付宝交易号：202608160001
```

支付流水表常见字段：

| 字段 | 含义 |
| --- | --- |
| flow_id | 系统内部流水号 |
| order_id | 关联的业务订单号 |
| flow_type | 流水类型，例如支付、退款 |
| direction | 资金方向，例如收入、支出 |
| amount | 流水金额 |
| pay_channel | 支付渠道，例如微信、支付宝、银行卡、余额 |
| request_no | 幂等请求号 |
| channel_trade_no | 第三方支付平台交易号 |
| channel_refund_no | 第三方退款单号 |
| status | 流水状态 |
| fail_reason | 失败原因 |
| created_at | 创建时间 |
| success_at | 成功时间 |

流水状态通常包括：

```text
处理中
成功
失败
关闭
```

流水表的核心作用是记录资金过程与资金事实。

---

## 4. 订单和流水的本质区别

| 对比项 | 订单 | 流水 |
| --- | --- | --- |
| 关注点 | 业务交易 | 资金动作 |
| 描述对象 | 用户买了什么 | 钱发生了什么变化 |
| 数据粒度 | 一笔业务订单 | 一次资金操作 |
| 常见关系 | 一条订单记录 | 多条流水记录 |
| 状态含义 | 业务状态 | 支付或资金状态 |
| 是否频繁对账 | 一般不直接用于支付对账 | 经常用于支付对账 |
| 是否可替代对方 | 不可以 | 不可以 |

订单回答的是：

```text
这个用户的这笔交易现在走到哪一步了？
```

流水回答的是：

```text
这笔交易相关的钱，每一次是怎么动的？
```

## 5. 为什么一个订单会对应多条流水

不能简单认为一个订单只对应一条流水。

原因是真实支付过程可能很复杂。

### 5.1 支付失败后重新支付

用户提交订单，应付 100 元。

第一次使用微信支付失败，第二次使用支付宝支付成功。

订单表：

```text
订单 O1001
应付金额：100
订单状态：已支付
```

流水表：

| 流水号 | 订单号 | 类型 | 金额 | 渠道 | 状态 |
| --- | --- | --- | --- | --- | --- |
| F001 | O1001 | 支付 | 100 | 微信 | 失败 |
| F002 | O1001 | 支付 | 100 | 支付宝 | 成功 |

如果只看订单表，只能知道订单最终支付成功。  
如果看流水表，才能知道中间发生过一次失败支付。

### 5.2 一个订单发生多次退款

订单支付 100 元，用户后来分两次退款。

流水表可能是：

| 流水号 | 订单号 | 类型 | 金额 | 状态 |
| --- | --- | --- | --- | --- |
| F001 | O1001 | 支付 | 100 | 成功 |
| F002 | O1001 | 退款 | 30 | 成功 |
| F003 | O1001 | 退款 | 70 | 成功 |

订单表最终可能是：

```text
订单 O1001
应付金额：100
已支付金额：100
已退款金额：100
订单状态：已退款
```

订单表保存的是汇总结果，流水表保存的是每一次资金动作明细。

### 5.3 混合支付

一个订单 100 元，用户用余额支付 40 元，再用支付宝支付 60 元。

流水表可能是：

| 流水号 | 订单号 | 类型 | 金额 | 渠道 | 状态 |
| --- | --- | --- | --- | --- | --- |
| F001 | O1001 | 支付 | 40 | 余额 | 成功 |
| F002 | O1001 | 支付 | 60 | 支付宝 | 成功 |

这种情况下，一个订单天然对应多条支付流水。

### 5.4 分账和手续费

用户支付 100 元，平台收取 5 元手续费，商户入账 95 元。

可能产生：

| 流水号 | 类型 | 金额 | 说明 |
| --- | --- | --- | --- |
| F001 | 用户支付 | 100 | 用户付款 |
| F002 | 平台手续费 | 5 | 平台收入 |
| F003 | 商户入账 | 95 | 商户待结算金额 |

这类流水已经不只是支付流水，还可能涉及账户流水、财务流水或结算流水。

## 6. 典型业务流转

### 6.1 下单

用户提交订单。

订单表：

```text
订单号：O1001
应付金额：100
状态：待支付
```

流水表：

```text
暂无流水
```

有些系统会在创建支付单时提前生成一条处理中流水，具体取决于系统设计。

### 6.2 发起支付

用户选择微信、支付宝、银行卡等支付方式。

订单表：

```text
订单号：O1001
状态：待支付
```

流水表：

```text
流水号：F001
订单号：O1001
类型：支付
金额：100
渠道：支付宝
状态：处理中
```

### 6.3 支付成功

第三方支付平台异步回调系统，通知支付成功。

流水表更新：

```text
流水号：F001
状态：成功
第三方交易号：202608160001
成功时间：2026-08-16 10:00:00
```

订单表更新：

```text
订单号：O1001
状态：已支付
已支付金额：100
支付成功时间：2026-08-16 10:00:00
```

### 6.4 发起退款

用户申请退款 30 元。

流水表新增：

```text
流水号：F002
订单号：O1001
类型：退款
金额：30
状态：处理中
```

订单表可以更新为：

```text
订单号：O1001
退款中金额：30
状态：退款中
```

### 6.5 退款成功

第三方支付平台通知退款成功。

流水表更新：

```text
流水号：F002
状态：成功
成功时间：2026-08-16 10:10:00
```

订单表更新：

```text
订单号：O1001
已退款金额：30
状态：部分退款
```

## 7. 三类编号不要混淆

支付业务中经常会出现多个编号。

| 编号 | 来源 | 用途 |
| --- | --- | --- |
| 订单号 order_id | 电商业务系统生成 | 标识一笔业务订单 |
| 流水号 flow_id | 支付或账务系统生成 | 标识一次资金动作 |
| 第三方交易号 channel_trade_no | 微信、支付宝、银行等返回 | 标识第三方支付平台中的交易 |

示例：

```text
订单号：O1001
支付流水号：F9001
支付宝交易号：202608160001
```

这三个编号不是同一个东西。

一个订单号可以对应多条流水号。  
一条支付流水通常对应一个第三方交易号。  
一条退款流水通常也会对应一个第三方退款单号。

## 8. 常见表设计

### 8.1 简化设计

小型系统中，可能只有两张表：

```text
order
payment_flow
```

关系如下：

```text
order.order_id = payment_flow.order_id
```

这种设计适合业务复杂度不高的场景。

### 8.2 更完整的设计

复杂系统中，通常会拆得更细：

```text
业务订单表 order
支付单表 payment_order
支付流水表 payment_flow
账户流水表 account_flow
退款单表 refund_order
退款流水表 refund_flow
```

它们的职责可以这样理解：

| 表 | 职责 |
| --- | --- |
| order | 记录用户买了什么、订单状态是什么 |
| payment_order | 记录本次需要收多少钱 |
| payment_flow | 记录每次调支付渠道的请求和结果 |
| refund_order | 记录退款申请和退款业务状态 |
| refund_flow | 记录每次退款渠道请求和结果 |
| account_flow | 记录账户余额、商户账务、平台账务变化 |

关系示例：

```text
order 1 : N payment_order
payment_order 1 : N payment_flow
order 1 : N refund_order
refund_order 1 : N refund_flow
order 1 : N account_flow
```

并不是所有系统都需要这么拆。拆表的目的是让业务订单、支付渠道交互、账户账务各自独立，避免一张表承担过多职责。

## 9. 订单状态和流水状态的关系

订单状态通常由成功的流水驱动，但不能直接等同于流水状态。

例如：

| 场景 | 流水状态 | 订单状态 |
| --- | --- | --- |
| 刚下单未支付 | 无流水或支付流水处理中 | 待支付 |
| 支付失败 | 支付流水失败 | 待支付或已取消 |
| 支付成功 | 支付流水成功 | 已支付 |
| 部分退款成功 | 退款流水成功 | 部分退款 |
| 全部退款成功 | 退款流水成功 | 已退款 |

需要注意：

- 支付流水成功，一般会推动订单变为已支付。
- 支付流水失败，不一定会让订单取消，用户可能还可以继续支付。
- 退款流水成功，会推动订单的退款金额和退款状态变化。
- 多条流水同时存在时，订单状态通常是根据成功流水聚合出来的结果。

## 10. 为什么必须保留流水

流水在支付系统中非常重要，不能只依赖订单表。

主要原因包括：

### 10.1 对账

系统需要拿自己的流水和微信、支付宝、银行的账单进行核对。

如果第三方账单里有一笔支付成功，而系统订单还是未支付，就需要排查：

- 是否漏处理回调
- 是否回调处理失败
- 是否订单状态更新失败
- 是否存在重复支付

### 10.2 幂等

第三方支付回调可能重复发送。

如果没有流水表，就很难判断这次回调之前是否已经处理过。

常见做法是：

```text
根据支付流水号、第三方交易号、回调通知号做幂等控制。
同一笔成功回调只能把订单从待支付更新为已支付一次。
```

### 10.3 客服排查

用户反馈“我已经付款了，但订单还是未支付”。

这时需要查：

- 是否有支付流水
- 支付流水状态是什么
- 第三方交易号是什么
- 支付渠道是否返回成功
- 回调是否到达
- 回调处理是否报错

这些信息都不适合只放在订单表里。

### 10.4 审计和财务

流水是资金事实的记录。

财务、审计、风控通常需要查看资金动作明细，而不是只看订单最终状态。

订单可以取消、关闭、退款，但流水应该尽量保留完整历史。

## 11. 设计建议

### 11.1 订单表保存业务汇总状态

订单表适合保存：

- 应付金额
- 已支付金额
- 已退款金额
- 订单状态
- 支付成功时间
- 订单完成时间
- 订单取消时间

订单表不适合记录所有支付尝试明细。

### 11.2 流水表保存资金明细

流水表适合保存：

- 每一次支付请求
- 每一次支付结果
- 每一次退款请求
- 每一次退款结果
- 支付渠道
- 第三方交易号
- 失败原因
- 回调原始关键信息

流水表不应该只保存最终成功的一笔，否则排查问题和对账都会困难。

### 11.3 流水号要全局唯一

流水号建议系统内部生成，并保证唯一。

常见要求：

- 全局唯一
- 可用于幂等
- 可用于对账
- 可追踪一次资金动作

不要直接依赖订单号作为流水号，因为一个订单可能产生多条流水。

### 11.4 金额字段要明确含义

订单表里的金额和流水表里的金额含义不同。

订单表：

```text
pay_amount = 这笔订单应付多少钱
paid_amount = 这笔订单已经成功支付多少钱
refunded_amount = 这笔订单已经成功退款多少钱
```

流水表：

```text
amount = 这一次资金动作的金额
```

不要把订单金额和流水金额混为一谈。

### 11.5 支付成功要事务化处理

支付成功回调后，通常至少要做两件事：

```text
1. 更新支付流水为成功
2. 更新订单为已支付
```

这两个动作应尽量放在同一个本地事务里。

如果还涉及发消息、加积分、发优惠券、通知仓库等后续动作，建议通过消息队列或事件机制异步处理，避免支付回调链路过长。

### 11.6 退款金额不能超过已支付金额

退款时需要校验：

```text
本次退款金额 + 已成功退款金额 <= 已成功支付金额
```

如果允许多次退款，这个校验必须可靠，否则会发生超退。

## 12. 一个完整例子

用户购买商品，应付 100 元。

第一次用微信支付失败。  
第二次用支付宝支付成功。  
后来申请退款 30 元。  
最后又退款 70 元。

订单表最终结果：

| 订单号 | 应付金额 | 已支付金额 | 已退款金额 | 状态 |
| --- | --- | --- | --- | --- |
| O1001 | 100 | 100 | 100 | 已退款 |

流水表完整明细：

| 流水号 | 订单号 | 类型 | 金额 | 渠道 | 状态 |
| --- | --- | --- | --- | --- | --- |
| F001 | O1001 | 支付 | 100 | 微信 | 失败 |
| F002 | O1001 | 支付 | 100 | 支付宝 | 成功 |
| F003 | O1001 | 退款 | 30 | 支付宝 | 成功 |
| F004 | O1001 | 退款 | 70 | 支付宝 | 成功 |

从这个例子可以看出：

- 订单表只保留当前业务结果。
- 流水表保留每一次资金动作。
- 订单金额不等于每条流水金额。
- 一个订单可以有多条支付、退款流水。

## 13. 常见误区

### 13.1 误区一：一个订单只会有一条流水

真实业务中经常不是这样。

支付失败重试、混合支付、多次退款、分账、手续费都会让一个订单对应多条流水。

### 13.2 误区二：订单状态成功就代表资金一定没问题

不一定。

订单状态可能因为系统异常、回调重复、事务失败、人工处理等原因和真实资金状态不一致。

所以支付系统必须做对账。

### 13.3 误区三：流水表只记录成功记录

不建议。

失败、处理中、关闭等状态也有价值，尤其在排查支付问题时非常重要。

### 13.4 误区四：第三方交易号可以当作内部流水号

不建议。

内部系统应该有自己的流水号。第三方交易号是外部渠道返回的编号，可以作为对账字段，但不应该替代内部流水号。

---

## 14. 总结

订单和流水的关系可以概括为：

```text
订单 = 业务交易主记录
流水 = 资金动作明细记录
```

订单表关注业务结果，流水表关注资金过程。

一个订单通常可以对应多条流水：

```text
支付流水
退款流水
账户流水
手续费流水
分账流水
结算流水
```

订单状态可以由成功流水驱动，但订单不能替代流水，流水也不能替代订单。

在系统设计中，建议让订单表承担业务状态职责，让流水表承担资金明细、对账、审计和问题排查职责。
