# 交易支付与电商防资损设计详解

## 1. 核心结论

交易支付和电商业务中的“不资损”，不是依赖某一个技术点，而是一整套体系。

核心目标是：

```text
不该收的钱不能收
该收的钱不能少收
不该退的钱不能退
该退的钱不能多退
没支付不能发货
重复回调不能重复记账
重复请求不能重复下单、重复扣款、重复退款
系统异常后账能对得上，问题能补回来
```

可以概括为：

```text
资损防控 = 事前防错 + 事中幂等和状态控制 + 事后对账补偿
```

真正可靠的交易系统不是假设永不失败，而是：

```text
任何一步失败后，都能被发现、被追踪、被修正。
```

---

## 2. 什么是资损

资损不是只有“钱被盗了”才算。

只要导致平台、用户、商户、支付渠道之间金额不一致，都属于资损风险。

常见资损场景：

```text
用户没付款，订单却发货了
用户付款 100，系统只记了 90
用户付款失败，订单却变成已支付
用户只付了一次，系统给商户入账两次
用户退款 30，系统退了 60
订单已全额退款，又重复退款一次
优惠券重复使用
库存超卖后平台赔付
支付渠道成功了，但系统订单还是未支付
系统订单显示支付成功，但渠道没有这笔钱
商户结算金额算错
手续费、分账、佣金计算错
```

资损可以发生在：

```text
下单
支付
退款
库存
优惠券
账户余额
商户结算
营销补贴
人工操作
```

所以防资损不是支付系统一个团队的事，而是交易链路整体设计的问题。

## 3. 基础原则

交易支付系统里有几个底层原则。

### 3.1 前端数据不可信

前端提交的数据只能作为选择项，不能作为最终金额依据。

例如前端提交：

```text
商品价格 = 100
优惠金额 = 20
应付金额 = 80
```

服务端不能直接相信。

服务端必须重新计算：

```text
商品价格
运费
优惠
活动价
限购
应付金额
```

### 3.2 金额以服务端计算为准

订单金额、支付金额、退款金额都应该由服务端计算并落库。

支付时传给微信、支付宝的金额，必须来自服务端的支付单。

### 3.3 支付成功以渠道结果为准

不能因为前端跳转到“支付成功页”，就把订单改成已支付。

支付成功必须以：

```text
微信/支付宝/银行异步回调
或主动查单结果
```

为准。

### 3.4 所有外部通知都可能重复

这些都可能重复：

```text
支付回调
退款回调
MQ 消息
RPC 重试
前端重复提交
定时任务重复执行
```

所以必须幂等。

### 3.5 缓存不是最终事实

Redis 可以用于库存预扣、限流、幂等标记，但最终交易事实应该落数据库。

最终事实包括：

```text
订单
支付单
支付流水
退款单
退款流水
账户流水
库存锁定明细
优惠券使用记录
```

### 3.6 对账不能省

线上链路负责尽量不出错。

对账系统负责发现错误。

补偿系统负责修正错误。

没有对账的支付系统，本质上没有最后防线。

## 4. 表模型防资损

防资损的第一步是表模型职责清晰。

不要只用一张订单表承载所有交易、支付、退款、账务信息。

推荐核心表：

```text
order              业务订单表
order_item         订单商品明细表
payment_order      支付订单表
payment_flow       支付流水表
refund_order       退款订单表
refund_flow        退款流水表
account_flow       账户流水 / 财务流水表
```

各表职责：

| 表 | 职责 |
| --- | --- |
| order | 记录买卖业务状态 |
| order_item | 记录订单商品快照、商品级状态 |
| payment_order | 记录本次收款任务 |
| payment_flow | 记录每一次支付渠道请求和结果 |
| refund_order | 记录退款业务申请 |
| refund_flow | 记录每一次退款渠道请求和结果 |
| account_flow | 记录账户资金变化 |

关键原则：

```text
订单表记录业务状态。
流水表记录资金动作。
账户流水记录钱的变化。
```

不要只靠订单状态判断资金事实。

例如订单是 `PAID`，还应该能查到：

```text
成功支付流水
第三方交易号
支付金额
支付渠道
支付回调时间
账户入账流水
```

## 5. 金额防错

金额是资损高发点。

### 5.1 金额类型

金额字段建议使用：

```text
分为单位的整数
或 BigDecimal
```

不要使用：

```text
float
double
```

因为浮点数有精度问题。

### 5.2 金额字段含义要清晰

订单金额常见字段：

```text
goods_amount       商品总金额
discount_amount    优惠金额
freight_amount     运费
pay_amount         应付金额
paid_amount        已支付金额
refunded_amount    已退款金额
```

基本校验：

```text
pay_amount = goods_amount + freight_amount - discount_amount
```

支付金额校验：

```text
payment_order.pay_amount = order.pay_amount
payment_flow.amount = 本次支付金额
渠道回调金额 = payment_flow.amount
```

退款金额校验：

```text
本次退款金额 + 已成功退款金额 <= 已成功支付金额
```

### 5.3 防超退 SQL

退款更新时要用条件更新。

示例：

```sql
update order
set refunded_amount = refunded_amount + #{refundAmount}
where order_id = #{orderId}
  and paid_amount >= refunded_amount + #{refundAmount};
```

如果更新行数为 1，说明退款金额合法。

如果更新行数为 0，说明可能出现：

```text
超退
重复退款
并发退款
订单状态不允许退款
```

## 6. 幂等防重复资损

支付和退款系统中，重复是常态。

必须假设这些情况一定会发生：

```text
用户重复点击
接口超时后重试
支付回调重复通知
退款回调重复通知
MQ 重复投递
定时任务重复扫描
```

### 6.1 常见幂等键

| 幂等键 | 场景 |
| --- | --- |
| request_no | 业务请求幂等 |
| order_id | 业务订单幂等 |
| pay_order_id | 支付单幂等 |
| payment_flow_id | 支付流水幂等 |
| refund_order_id | 退款单幂等 |
| refund_flow_id | 退款流水幂等 |
| channel_trade_no | 第三方支付交易幂等 |
| channel_refund_no | 第三方退款交易幂等 |
| message_id | MQ 消费幂等 |

### 6.2 支付回调幂等

支付成功回调更新流水：

```sql
update payment_flow
set status = 'SUCCESS',
    channel_trade_no = #{channelTradeNo},
    success_at = now()
where flow_id = #{flowId}
  and status in ('INIT', 'PAYING');
```

如果更新行数为 1：

```text
第一次处理成功，可以继续推进 payment_order 和 order。
```

如果更新行数为 0：

```text
说明已经处理过，直接返回成功给支付渠道。
```

支付渠道要求回调方成功处理后返回成功响应。

如果重复回调时返回失败，渠道可能继续重试，造成更多噪音。

### 6.3 退款回调幂等

退款成功回调更新退款流水：

```sql
update refund_flow
set status = 'SUCCESS',
    channel_refund_no = #{channelRefundNo},
    success_at = now()
where refund_flow_id = #{refundFlowId}
  and status = 'REFUNDING';
```

只有第一次成功更新时，才能继续：

```text
更新 refund_order
增加 order.refunded_amount
生成账户出账流水
```

### 6.4 MQ 消费幂等

MQ 通常是至少一次投递。

消费者必须能处理重复消息。

可以使用消费记录表：

```text
mq_consume_log
- message_id
- consumer_group
- biz_id
- status
- created_at
```

也可以依赖业务唯一键，例如：

```text
同一 order_id 只能发货一次
同一 payment_flow_id 只能入账一次
同一 refund_flow_id 只能出账一次
```

## 7. 状态机防乱流转

状态机必须单向、可控。

### 7.1 订单状态机

常见订单状态：

```text
WAIT_PAY -> PAID -> SHIPPED -> COMPLETED
WAIT_PAY -> CANCELED
PAID -> PART_REFUNDED
PAID -> REFUNDED
```

不应该允许：

```text
CANCELED -> PAID
REFUNDED -> PAID
COMPLETED -> WAIT_PAY
```

支付成功更新订单时带状态条件：

```sql
update order
set status = 'PAID',
    paid_amount = #{payAmount},
    paid_at = now()
where order_id = #{orderId}
  and status = 'WAIT_PAY';
```

### 7.2 支付单状态机

支付单状态：

```text
WAIT_PAY -> PAYING -> PAID
WAIT_PAY -> CLOSED
PAYING -> FAILED
PAYING -> PAID
```

不能允许：

```text
PAID -> WAIT_PAY
CLOSED -> PAID
```

### 7.3 退款单状态机

退款单状态：

```text
WAIT_AUDIT -> WAIT_REFUND -> REFUNDING -> SUCCESS
REFUNDING -> FAILED
WAIT_AUDIT -> REJECTED
```

退款成功必须从 `REFUNDING` 推进到 `SUCCESS`。

不能让已经成功的退款单再次进入退款中。

### 7.4 库存状态机

库存锁定明细：

```text
LOCKED -> CONFIRMED
LOCKED -> RELEASED
LOCKED -> EXPIRED
```

不能允许：

```text
CONFIRMED -> RELEASED
RELEASED -> CONFIRMED
```

支付成功时：

```text
LOCKED -> CONFIRMED
```

订单超时或取消时：

```text
LOCKED -> RELEASED / EXPIRED
```

这样可以避免支付成功后又被超时任务释放库存。

## 8. 本地事务保证局部一致

单个服务内部必须用本地事务保证关键数据一起成功或一起失败。

### 8.1 支付成功本地事务

支付成功回调时：

```text
开启本地事务
  -> payment_flow = SUCCESS
  -> payment_order = PAID
  -> order = PAID
  -> account_flow 入账
提交事务
```

如果这些表不在一个服务或一个库中，则不能靠一个本地事务，需要事件驱动或分布式事务方案。

### 8.2 退款成功本地事务

退款成功时：

```text
开启本地事务
  -> refund_flow = SUCCESS
  -> refund_order = SUCCESS
  -> order.refunded_amount 增加
  -> account_flow 出账
提交事务
```

### 8.3 不要把第三方接口放进数据库事务

不推荐：

```text
开启事务
  -> 插入支付流水
  -> 调用微信/支付宝
  -> 更新订单
提交事务
```

原因：

```text
外部接口不可控
事务时间过长
数据库锁持有太久
接口超时后状态不确定
```

推荐：

```text
先落本地流水
提交事务
调用第三方
通过回调或查单确认最终结果
```

## 9. 微服务分布式一致性

微服务下，订单、库存、支付、营销可能分属不同服务和数据库。

常见方案：

```text
本地事务 + Outbox + MQ
TCC
Saga
Seata AT/XA
补偿任务
```

### 9.1 Outbox + MQ

例如支付成功后：

```text
支付服务本地事务：
  payment_flow = SUCCESS
  payment_order = PAID
  写 outbox: PaymentSucceeded

后台任务投递 MQ：
  PaymentSucceeded

消费者：
  订单服务更新订单
  库存服务确认库存
  营销服务核销优惠
  积分服务加积分
```

Outbox 的价值是保证：

```text
本地状态更新成功，消息最终一定能发出去。
```

### 9.2 TCC

TCC 适合资源预留。

库存：

```text
Try：available_stock -> locked_stock
Confirm：locked_stock -> sold_stock
Cancel：locked_stock -> available_stock
```

账户：

```text
Try：可用余额 -> 冻结余额
Confirm：冻结余额 -> 扣减完成
Cancel：冻结余额 -> 可用余额
```

TCC 需要处理：

```text
幂等
空回滚
悬挂
防并发
```

### 9.3 Saga

Saga 适合长流程。

例如：

```text
创建订单成功
预占库存成功
创建支付单失败
  -> 补偿释放库存
  -> 补偿取消订单
```

Saga 是最终一致，不是严格强一致。

### 9.4 Seata AT/XA

Seata 可以用于普通订单链路中的分布式数据库事务。

但要注意：

```text
Seata 解决的是分布式事务一致性。
Seata 不解决秒杀削峰。
Seata 不能把微信、支付宝这类外部系统纳入数据库事务。
```

秒杀、爆品、热点库存更推荐：

```text
Redis Lua 预扣 + MQ 异步下单 + 幂等 + 补偿对账
```

## 10. 库存、优惠、活动名额防资损

库存不是资金，但库存错误会间接造成资损。

例如：

```text
超卖后平台赔付
优惠券重复使用导致补贴损失
活动名额超发导致履约失败
```

### 10.1 库存流转

推荐库存模型：

```text
下单：available_stock -> locked_stock
支付成功：locked_stock -> sold_stock
取消超时：locked_stock -> available_stock
```

库存锁定明细：

```text
stock_lock
- order_id
- user_id
- sku_id
- quantity
- status: LOCKED / CONFIRMED / RELEASED / EXPIRED
```

### 10.2 优惠券流转

优惠券状态：

```text
AVAILABLE -> LOCKED -> USED
LOCKED -> AVAILABLE
```

含义：

```text
下单时锁定优惠券
支付成功后核销优惠券
订单取消或超时后释放优惠券
```

防资损点：

```text
优惠券不能重复使用
优惠金额不能超过订单金额
优惠券必须和订单绑定
取消订单必须释放未使用优惠券
支付成功后不能再释放优惠券
```

### 10.3 活动名额流转

活动名额：

```text
available_quota -> locked_quota -> used_quota
locked_quota -> available_quota
```

活动名额也要有锁定明细：

```text
activity_quota_lock
- activity_id
- order_id
- user_id
- quantity
- status
```

## 11. 账户和账务防资损

如果系统涉及钱包余额、商户账户、平台收入、佣金、分账，必须有账户流水或记账分录。

不要只更新账户余额。

### 11.1 账户流水

示例字段：

```text
account_flow
- flow_id
- account_id
- biz_order_id
- biz_type
- amount
- direction
- balance_before
- balance_after
- flow_type
- status
- created_at
```

账户更新要保证：

```text
余额不能扣成负数
每次余额变化都要有流水
流水和业务单据能互相追溯
```

### 11.2 复式记账思想

例如用户支付 100，平台抽佣 5，商户入账 95：

```text
用户账户：-100
商户待结算账户：+95
平台手续费收入：+5
```

更严谨可以做分录：

```text
debit_account
credit_account
amount
biz_type
biz_id
```

核心原则：

```text
有入必有出
借贷平衡
余额不能无来源增加
余额不能无原因减少
每笔账都能追溯到业务单据
```

## 12. 对账系统

对账是防资损的最后防线。

### 12.1 常见对账关系

| 对账项 | 说明 |
| --- | --- |
| 支付渠道账单 vs payment_flow | 核对支付成功记录 |
| 退款渠道账单 vs refund_flow | 核对退款成功记录 |
| order vs payment_order | 核对订单金额和支付金额 |
| payment_order vs account_flow | 核对支付入账 |
| refund_order vs account_flow | 核对退款出账 |
| 商户结算单 vs 商户账户流水 | 核对结算金额 |
| stock_lock vs order | 核对库存锁定和订单状态 |
| 优惠券记录 vs order | 核对优惠券使用状态 |

### 12.2 对账类型

```text
实时对账：支付回调时校验金额、订单号、商户号
准实时对账：定时查单
日终对账：下载微信/支付宝/银行账单 T+1 核对
财务对账：账户流水、结算单、手续费核对
```

### 12.3 常见差错

```text
我方成功，渠道无记录
渠道成功，我方未成功
金额不一致
重复支付
重复退款
退款成功但订单未更新
订单已取消但渠道支付成功
账户流水缺失
商户结算金额不一致
```

### 12.4 差错处理

对账发现差错后，要进入差错处理流程：

```text
自动补单
自动关单
自动退款
自动补账户流水
人工审核
生成差错单
补偿任务重试
```

差错不能只打印日志。

必须有：

```text
差错记录
处理状态
处理人
处理时间
处理结果
审计日志
```

## 13. 风控和限额

防资损还要有风控。

常见策略：

```text
单笔支付限额
单日退款限额
用户退款频次限制
商户提现限额
优惠券使用限制
异常 IP / 设备限制
短时间重复下单限制
价格异常拦截
0 元订单审核
大额退款人工审核
批量退款人工审核
敏感操作双人复核
```

特别是退款、补贴、商户结算、人工调账，要有审批和审计。

人工操作必须记录：

```text
操作人
操作时间
操作前数据
操作后数据
操作原因
审批单号
```

## 14. 监控告警

防资损系统要监控业务资金指标，而不只是接口 QPS。

关键指标：

```text
支付成功金额突增/突降
退款金额突增
退款率异常
支付成功但订单未支付数量
订单已支付但无支付流水数量
渠道成功但我方失败数量
重复支付回调数量
重复退款请求数量
账户余额负数
库存 locked 长时间未释放
MQ 堆积
补偿任务失败数
对账差错数
商户结算差异数
```

告警要尽量接近实时。

特别是这些指标：

```text
账户余额负数
超退拦截失败
支付成功订单未更新
渠道成功我方失败
重复入账
重复退款
```

应该按高优先级处理。

## 15. 测试和演练

资损防控不能只测成功流程。

必须覆盖异常流程。

测试场景：

```text
支付回调重复
支付回调乱序
支付回调延迟
支付成功但订单更新失败
支付成功但 MQ 发送失败
退款重复回调
退款并发申请
订单取消和支付成功同时发生
Redis 扣成功但 DB 失败
MQ 重复消费
MQ 消费失败后重试
库存释放重复执行
优惠券重复核销
账户流水入账失败
渠道账单金额和我方金额不一致
```

演练重点：

```text
补偿任务是否能修正
对账系统是否能发现
告警是否能及时触达
人工差错流程是否闭环
```

## 16. 防资损设计清单

可以用下面这份清单检查系统。

### 16.1 下单

```text
服务端重新计算金额
保存订单商品快照
库存预占成功后才允许待支付
优惠券锁定成功后才允许待支付
订单创建幂等
购物车清理异步重试，不影响订单主流程
```

### 16.2 支付

```text
支付金额来自 payment_order
支付流水唯一
支付回调验签
校验渠道金额、商户号、订单号
支付回调幂等
支付成功状态更新带条件
支付成功后写账户流水
支付成功事件通过 Outbox/MQ 通知下游
```

### 16.3 退款

```text
退款单唯一
退款流水唯一
退款金额不能超过可退金额
退款回调验签
退款回调幂等
并发退款用条件更新控制
退款成功后更新 refunded_amount
退款成功后写账户出账流水
大额退款需要审批
```

### 16.4 库存和优惠

```text
库存有锁定明细
优惠券有锁定/使用记录
支付成功后 confirmed/used
订单取消后 released/available
重复取消不能重复释放
支付成功后不能再释放
```

### 16.5 账务

```text
每次余额变化都有流水
余额不能为负
流水和业务单据可追溯
商户结算有明细
手续费、佣金、分账可核对
```

### 16.6 对账补偿

```text
支付渠道对账
退款渠道对账
订单支付对账
账户流水对账
商户结算对账
差错单闭环
补偿任务可重试
人工处理有审计
```

## 17. 总结

交易支付和电商防资损的核心方案：

```text
1. 服务端权威计算金额
2. 清晰拆分订单、支付单、流水、退款单、账务流水
3. 所有请求、回调、消息都做幂等
4. 状态机单向流转，更新带状态条件
5. 本地事务保证单服务内部一致
6. 微服务之间用 MQ / Saga / TCC / Seata / Outbox 做最终一致
7. 库存、优惠、活动名额使用锁定明细
8. 退款严格校验可退金额，防超退和重复退
9. 账户体系使用流水和复式记账思想
10. 支付渠道、退款渠道、订单、账务必须定期对账
11. 异常要有补偿任务和差错处理
12. 关键资金指标必须监控告警
```

最终一句话：

**线上链路负责尽量不出错，对账系统负责发现错误，补偿系统负责把错误修回来。交易支付系统的可靠性不是来自“永不失败”，而是来自失败后仍然能闭环。**
