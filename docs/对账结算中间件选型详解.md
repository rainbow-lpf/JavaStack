# 对账结算中间件选型详解

## 1. 核心结论

在四方支付、服务商分润、上游对账、结算这些场景里，Doris / ClickHouse / StarRocks / Spark / Flink 不是互相替代的单品，而是分工不同的几类工具。

可以先这样理解：

```text
Doris / ClickHouse / StarRocks：存和查大规模对账明细、汇总、差错
Flink：实时处理交易事件、做窗口聚合、做准实时对账
Spark：离线批处理、历史回补、大批量重算
Kafka / RocketMQ：传递交易、退款、分润事件
```

在你们的对账结算链路里，最关键的是三件事：

```text
1. 交易发生时不要等结算再算分润，先生成分润明细
2. 对账不要直接压 MySQL，全量大表应该进入 OLAP / 批流计算层
3. 结算不要扫原始交易表现算，应该汇总已确认、未结算的分润账户流水
```

---

## 2. 为什么需要这些中间件

你们这种服务商模式，不是简单电商订单统计，而是：

```text
交易成功
  -> 生成分润明细
  -> T+1 导入上游账单
  -> 交易对账
  -> 分润对账
  -> 结算入账对账
  -> 生成结算单
  -> 给下级服务商打款
```

如果直接用 MySQL + 定时任务全量扫表，通常会遇到：

```text
扫表慢
join 慢
重跑慢
账期一大就压垮线上库
差异定位慢
历史数据越来越慢
```

所以需要把职责拆开：

```text
在线交易库：承接支付、退款、订单、账户写入
实时流处理：承接交易事件，提前计算分润和小时汇总
OLAP 分析库：承接明细查询、汇总对账、差错查询、报表
离线计算引擎：承接 T+1 账单、历史回补、大批量重算
消息队列：连接各个阶段
```

---

## 3. 这几类中间件分别做什么

### 3.1 Kafka / RocketMQ

作用：

```text
承接支付成功、退款成功、分润生成、结算完成等业务事件
提供异步解耦
提供削峰
提供重试和死信
```

在你们场景里通常用来传：

```text
PaymentSucceeded
RefundSucceeded
ProfitCalculated
SettlementGenerated
```

为什么需要它：

```text
支付回调不能同步调用一堆下游
分润计算不能压在支付回调主链路
对账差错修正、结算通知需要异步化
```

### 3.2 Flink

作用：

```text
实时消费交易事件
按小时 / 15 分钟做窗口聚合
实时生成分润明细和小时汇总
做准实时对账
```

Flink 适合的原因：

```text
事件流式输入
状态计算
窗口聚合
checkpoint 容错
低延迟
```

在你们场景里，Flink 可以做：

```text
支付成功后实时计算分润
退款成功后实时生成反向分润
按小时聚合交易量和分润金额
提前发现账单差异
```

### 3.3 Spark

作用：

```text
离线批处理
历史账期回补
上游 T+1 账单大文件处理
大批量全量重算
复杂离线 join
```

Spark 适合的原因：

```text
一次性处理大批量数据
适合文件读取和离线批作业
适合历史回放
适合大规模清洗和重建差错表
```

在你们场景里，Spark 可以做：

```text
T+1 上游账单解析
历史账期重新跑分润
按天批量生成对账差异
从 OSS / HDFS / S3 读取上游账单文件
```

### 3.4 Doris / ClickHouse / StarRocks

作用：

```text
存大规模交易明细、上游账单明细、分润明细、结算候选数据、差错单
支持大范围 group by / sum / count / join
支持快速明细查询和汇总查询
```

它们是分析型数据库，适合：

```text
按账期查几千万行
按渠道、商户、服务商、hash bucket 做汇总
做汇总对账
做明细对账
查差错单
做结算试算
```

它们不适合：

```text
高频小事务写入
强依赖行级事务的在线扣减
频繁更新大量明细
```

## 4. 在对账链路里放在哪一层

可以把链路拆成四层。

### 4.1 在线交易层

```text
支付服务
退款服务
订单服务
分润服务
```

职责：

```text
落支付事实
落退款事实
生成分润明细
写本地流水
发布事件到 MQ
```

### 4.2 流处理层

```text
Kafka / RocketMQ + Flink
```

职责：

```text
消费交易事件
做实时去重
做小时级汇总
做准实时分润计算
写入 OLAP
```

### 4.3 分析存储层

```text
Doris / ClickHouse / StarRocks
```

职责：

```text
存我方交易明细
存上游账单明细
存分润明细
存汇总表
存差错单
存结算候选池
```

### 4.4 离线批处理层

```text
Spark
```

职责：

```text
T+1 上游账单导入
历史重跑
账期回补
全量重新计算
复杂 join 和大规模比对
```

## 5. 对账场景怎么落地

### 5.1 交易成功后

支付成功事件发生后：

```text
支付服务写 payment_flow 成功
发布 PaymentSucceeded
Flink 消费事件，生成 profit_detail
写入 Doris / ClickHouse / StarRocks
```

这样对账时不会再从 payment_flow 重新现算分润。

### 5.2 上游账单导入

T+1 上游发来账单文件：

```text
OSS / S3 / HDFS 落原始文件
Spark 批量解析
写 channel_trade_bill_detail
写 channel_profit_bill_detail
写 channel_settle_bill_detail
同步到 OLAP
```

### 5.3 汇总对账

在 OLAP 里先做：

```text
按 bill_date + hour + channel + provider_id + hash_bucket 汇总
count
sum_amount
sum_fee
sum_profit
```

汇总一致的切片快速通过。

### 5.4 明细对账

如果汇总不一致，再做逐笔对比：

```text
local_trade_detail
vs
channel_trade_bill_detail
```

或者：

```text
profit_detail
vs
channel_profit_bill_detail
```

把差异写入 `reconcile_diff`。

### 5.5 结算生成

结算时，不扫原始交易表。

而是汇总：

```text
profit_account_flow
```

生成：

```text
settlement_order
settlement_detail
```

## 6. 订单量很大时怎么切

千万级每天时，不要把一个任务做成“全表大扫除”。

推荐切法：

```text
业务账期：按天
计算窗口：按小时或 15 分钟
并行粒度：按渠道 / 服务商 / 商户 / hash bucket
```

例如：

```text
bill_date = 2026-08-17
hour = 10
bucket = hash(channel_trade_no) % 128
```

这样一条大账期可以拆成很多小切片处理。

优点：

```text
并行快
失败可重跑
差异定位清楚
不会一把扫爆数据库
```

## 7. 为什么不是只用一个 Hera 任务

Hera 之类调度器的问题不是“不能用”，而是它只负责：

```text
什么时候跑
失败怎么重试
任务依赖怎么编排
```

它不负责：

```text
数据怎么切
join 怎么快
明细怎么存
怎么增量计算
怎么做 checkpoint
怎么做 OLAP 查询
```

所以更准确的说法是：

```text
调度器负责触发
Spark / Flink 负责计算
Doris / ClickHouse / StarRocks 负责存和查
Kafka / RocketMQ 负责传事件
```

## 8. 选型建议

### 8.1 需要准实时

如果你希望交易成功后几分钟内就能看到分润汇总或差异：

```text
Kafka + Flink + Doris/ClickHouse/StarRocks
```

### 8.2 需要 T+1 批处理

如果主要是日终对账、账单解析、历史回补：

```text
Spark + Doris/ClickHouse/StarRocks
```

### 8.3 需要海量明细检索

如果你经常查：

```text
某个账期
某个服务商
某个渠道
某个差错单
```

适合：

```text
Doris / ClickHouse / StarRocks
```

### 8.4 需要消息削峰

支付成功、退款成功、结算完成这些事件：

```text
Kafka / RocketMQ
```

## 9. 你们场景里的推荐组合

比较稳的组合是：

```text
在线交易库
  -> 交易成功 / 退款成功事件
  -> Kafka / RocketMQ
  -> Flink 实时计算分润和小时汇总
  -> Doris / ClickHouse / StarRocks

上游账单文件
  -> OSS / HDFS
  -> Spark 批量解析
  -> Doris / ClickHouse / StarRocks

对账服务
  -> 先汇总
  -> 再明细
  -> 生成 reconcile_diff

结算服务
  -> 汇总已确认未结算的 profit_account_flow
  -> 生成 settlement_order
```

这套组合的核心收益是：

```text
交易时预计算
对账时只做确认
结算时只做汇总
异常差错单独闭环
```

---

## 10. 面试怎么说

可以这样回答：

```text
我们不会把千万级对账压在 MySQL 或单个调度任务里。
在线交易发生后，通过 Kafka / RocketMQ 传事件，Flink 实时生成分润明细和小时汇总，写到 Doris / ClickHouse / StarRocks。
上游 T+1 账单通过 Spark 批量解析导入分析库。
对账时先在 OLAP 上按账期、小时、渠道、服务商、hash bucket 做汇总对账，汇总一致的切片直接通过，不一致的切片再做明细 join，生成 reconcile_diff。
结算时只汇总已确认、未结算的 profit_account_flow，不现场扫原始交易表重算。
调度器只负责触发，不负责核心计算。
```

补一句性能原则：

```text
真正的优化不是换调度器，而是把全量重算改成预计算、分区、分片、增量和差错闭环。
```

---

## 11. 总结

这几个中间件的分工可以记成一句话：

```text
Kafka / RocketMQ 负责传事件，
Flink 负责实时流计算，
Spark 负责离线批处理，
Doris / ClickHouse / StarRocks 负责海量对账和报表查询。
```

在你们的对账结算场景里，最重要的不是选某一个工具，而是：

```text
交易时预计算分润
对账时先汇总后明细
结算时汇总已确认流水
大表进入 OLAP
历史回补交给批处理
实时链路交给流处理
```

这样才能支撑日千万级甚至更高的数据量。
