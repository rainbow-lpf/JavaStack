# QPS 与千万级订单金额服务器部署面试回答

## 1. 面试场景

面试官经常会问：

```text
系统的 QPS 大概是多少？
订单金额达到千万级时，线上部署了多少台服务器？
节假日高峰期间如何扩容？
```

回答时不要只报机器数量，还要说明 QPS 口径、机器用途、服务拆分方式和高峰期容量策略。

## 2. 推荐回答

可以直接这样回答：

> 线上生产环境应用服务器大概 40-50 台，单机配置主要是 4 核 8G，整体采用微服务架构，拆分为大约 10 个业务服务。平时整体业务 QPS 在几百左右，节假日或活动高峰期间峰值大概在 1000-1500 QPS。
>
> 这里的 QPS 是平台入口业务接口的整体 QPS，不是某一个服务的 QPS。40-50 台是整个应用层集群规模，包含网关、订单、库存、支付、商品、用户、营销以及异步消费者等服务。各服务会进行多实例部署，订单、库存、支付等核心服务会配置更多副本。
>
> 节假日或大促前会根据历史流量提前扩容，具备条件的服务会通过容器平台进行自动扩容。数据库、Redis 和 MQ 属于独立集群，不包含在这 40-50 台应用服务器中。整体容量主要根据峰值 QPS、下单 TPS、支付 TPS、数据库写入 TPS 和接口响应时间进行评估，而不是只根据订单金额估算。

## 3. 规模口径

| 项目 | 规模或说明 |
| --- | --- |
| 应用服务器 | 40-50 台左右 |
| 单机配置 | 4 核 8G |
| 微服务数量 | 10 个左右 |
| 平时 QPS | 几百左右 |
| 节假日或活动峰值 | 1000-1500 QPS 左右 |
| 订单金额 | 千万级 GMV |
| 扩容方式 | 节前提前扩容，部分服务支持自动扩容 |
| 数据库、Redis、MQ | 独立集群，通常不计入应用服务器数量 |

## 4. 典型部署结构

```text

  |
微服务集群

  +-- 商品服务

  +-- 库存服务
  +-- 支付服务
  +-- 营销服务
  +-- 购物车服务
  +-- 售后服务
  +-- 后台服务
  +-- 异步任务与消息消费服务

  +-- Redis 集群
  +-- MQ 集群
  +-- MySQL 主从或分库分表集群
  +-- Elasticsearch / 对象存储 / 第三方支付
```

## 5. 为什么 1500 QPS 可以对应 40-50 台机器

从纯吞吐量角度看，1500 QPS 并不一定需要 40-50 台 4 核 8G 服务器。但这里的机器数量通常不是按照单个接口的吞吐量线性计算出来的，原因包括：

1. 40-50 台是整个应用集群的规模，不是一个服务独占的机器数量。
2. 微服务需要多实例部署，避免单点故障，并支持滚动发布。
3. 订单、库存、支付等核心服务通常需要更多实例和更高冗余。
4. 部分机器用于异步消费、定时任务、后台管理和运营活动服务。
5. 节假日或大促期间需要提前预留容量，不能把机器长期压到极限。
6. 生产系统还要考虑接口耗时、GC、连接池、线程池、网络 IO 和突发流量。

因此，应该表述为：

```text
40-50 台是整个生产应用集群规模，包含服务拆分、高可用、
异步任务和峰值容量预留，不是单纯为了支撑 1500 QPS 而线性堆出来的。
```

## 6. “订单金额千万”不能直接推导服务器数量

订单金额只能说明业务规模，不能直接说明技术流量。容量评估还需要结合客单价和订单数量。

例如：

```text
订单数量 = 总交易金额 / 平均客单价
```

如果总交易金额为 1000 万元：

```text
平均客单价 500 元，约为 2 万单
平均客单价 20 元，约为 50 万单
```

两种情况下的订单量、库存扣减量、支付请求量和数据库写入压力差异很大。因此面试时应强调：

```text
服务器规模主要按峰值 QPS、核心链路 TPS、接口耗时和资源利用率评估，
订单金额更多用于说明业务体量，不能单独作为容量依据。
```

## 7. 高峰期扩容回答方式

如果主要是节前人工增加实例，应说：

```text
节假日或大促前会根据历史数据和压测结果提前扩容。
```

如果使用了 Kubernetes HPA 或其他自动伸缩能力，可以说：

```text
核心服务配置了自动扩容策略，根据 CPU、内存、请求数或延迟指标
动态调整实例数量；对于大促等可预期流量，仍然会提前扩容，
避免完全依赖临时自动扩容。
```

不要在没有实际自动伸缩能力时直接说“动态扩容”，可以使用“提前扩容”或“弹性扩容”。

## 8. 面试追问与回答边界

### 8.1 1500 QPS 是哪个层面的 QPS？

建议回答：

> 这是平台入口业务接口的整体峰值 QPS。不同服务的 QPS 会有差异，商品查询、首页推荐等读请求通常较高，订单创建、库存扣减和支付请求相对较低，但对一致性和稳定性的要求更高。

### 8.2 40-50 台是否包含数据库？

建议回答：

> 40-50 台主要指应用层服务器。数据库、Redis、MQ、网关和其他基础设施会按照各自的高可用方案独立部署，具体是否计入总机器数需要看公司的统计口径。

### 8.3 为什么不用单体应用？

建议回答：

> 业务模块之间的流量特征和扩容需求不同。商品查询、订单、库存和支付的性能特征不一样，拆分后可以独立扩容、独立发布和故障隔离。核心链路同时会控制服务调用层级，避免微服务拆分导致链路过长。

### 8.4 如何保护数据库？

建议回答：

> 热点数据使用 Redis 缓存，非核心流程通过 MQ 异步削峰，数据库采用主从、读写分离或分库分表等方式扩展。订单和库存写入仍然以数据库最终一致性和幂等控制为基础，并配合限流、降级和重试机制。

## 9. 最终简短版本

当面试时间比较紧时，可以这样回答：

> 我们线上应用集群大概 40-50 台机器，单机 4 核 8G，采用微服务架构，拆分了 10 个左右的服务。平台平时 QPS 几百，节假日或活动高峰大概 1000-1500 QPS。40-50 台指整个应用层集群，不是单个服务，包含网关、订单、库存、支付、商品、用户、营销和异步消费等服务。核心服务多实例部署，高峰期会根据压测和历史流量提前扩容，部分服务支持自动扩容。数据库、Redis 和 MQ 是独立集群，容量评估主要看峰值 QPS、下单和支付 TPS，以及数据库写入压力，不能只看千万级订单金额。
